# Blocksmith

A block-survival game for the Nintendo 3DS, written from scratch in C against
libctru and citro3d.

<!-- readme-version: 1.9.2 -->

Nothing here is borrowed. No Minecraft assets, no ported code, no third-party
texture pack — every block texture, the font, the Home Menu art and the banner
chime are generated by the scripts in `tools/`, and every system below was
written for this project.

If the game ever crashes it writes `sdmc:/blocksmith/crash.txt`. If it stops
drawing frames without crashing, that is the watchdog's job instead and it
writes `sdmc:/blocksmith/hang.txt`, naming the phase the main thread was in.

## Install

The newest release is **v1.9.2**, and it is what the QR code, the direct link below and
**Options → Check for Update** all point at. It is a hotfix for v1.9.1, which could stop
answering the buttons after you made a world or resumed from the pause menu — install it
over v1.9.1. v1.9.0 was tagged but never given a Release of its own — everything in it ships
inside v1.9.2, so there is nothing to miss by skipping either.

**Scan the QR code above with FBI** ("Scan QR Code" → install). It points at the
`.cia` attached to the v1.9.2 release, so FBI downloads and installs it
directly.

Or download [`blocksmith1.9.2.cia`](https://github.com/stevenjc2009-byte/blocksmith/releases/tag/v1.9.2)
by hand, put it on your SD card, and install it with FBI.

Once it's installed, you don't need the QR again: **Options → Check for Update**
asks GitHub for the newest release, shows you what's in it on the top screen,
and installs it in place.

You need custom firmware (Luma3DS) to install a `.cia`. If you'd rather not
install anything, `blocksmith.3dsx` runs from the Homebrew Launcher instead.

## What's in it

* **An infinite world**, generated from seeded value noise — grass, dirt,
  stone, sand, wood, leaves, water and tall grass, with trees and 3D-noise
  caves. Planks are the one block the generator never places: they only exist
  once you craft them from wood.
* **Six biomes**, classified on a temperature/humidity rectangle: tundra,
  taiga, plains, forest, desert and jungle. The biome decides the surface
  material, how much grass grows, which plants appear and what shape the trees
  are. Tundra ground caps in snow, cold seas freeze over, cactus and dead bush
  scatter across the desert, and ferns grow in taiga and jungle.
* **Trees that differ by biome and by tree.** Three crown silhouettes — a
  round crown, a tiered conifer, a broad flat jungle canopy — and each tree
  picks its own trunk height, canopy width and tier count, with a 2 × 2 trunk
  where the biome allows it and the four ground columns under it are level.
* **Breaking a block takes time.** The break button is held, not tapped: every
  block has its own hardness in ticks at 20 TPS, and a crack spreads across the
  face while you work at it. Let go, look away, or have the block change under
  your crosshair and the progress is thrown away rather than carried over.
* **Place blocks** anywhere, via a DDA voxel raycast with a highlight cage on
  the targeted face.
* **Water that flows.** Sources spread on the simulation clock rather than
  filling instantly, through flow levels that fall off with distance. A surface
  cell is drawn seven-eighths of a block high instead of flush with the ground
  beside it, and water is see-through — alpha 0.70, drawn in a transparent pass
  — so a lake bottom and anything built underwater are visible from above, and
  a shoreline reads as a surface rather than a wall of blue cubes.
* **Animals.** Pigs, cows, chickens and sheep spawn in the world as you explore
  it. They can be hit and killed, and each drops raw meat you can eat.
* **Worlds that persist.** A region save format with CRC32 checksums and
  torn-write recovery, so a power cut during a write costs you that one region
  and nothing else.
* **Multiple worlds**, created and picked from a title screen. They keep their
  own saved edits and their own terrain: each single-player world gets a unique
  randomly minted seed, written to a sidecar, so each newly created world starts
  as a different landscape.
* **Multiplayer.** Connect from the title screen and you are in the server's
  world — its seed, and every block edit anyone has made in it. Terrain is never
  transmitted: each console generates the same landscape from the same seed and
  the server stores only the edits. The client subscribes to each column as the
  streaming ring loads it and the server answers with just that column's edits,
  paged across as many packets as they need — so a join costs a trickle of small
  edit packets bounded by your render distance, not a world download. Other
  players show up and move around, your edits reach them, and a session that ends
  tells you why.
* **A touchscreen inventory**, hotbar and a small crafting table — seven
  recipes: dirt → grass, stone → sand, leaves → dirt, wood → planks, coal
  ore → torch, stone → furnace, planks → chest.
* **Options that stick** — render distance, look sensitivity, inverted pitch,
  the 3D-slider depth, the debug menu toggle and every rebindable button, saved
  to `sdmc:/blocksmith/options.ini`.
* **A loading screen** with a real progress bar and live counters, so creating a
  world shows you what it is doing instead of sitting on a dead frame.
* **An in-app updater** — Options → Check for Update downloads the newest
  release straight from GitHub and installs it over itself. When one is
  available the top screen shows that release's change notes — what was added,
  what was fixed — scrollable with the D-pad, *before* you commit to the
  download.
* **A crash handler** that dumps the fault to the SD card instead of hanging,
  and a watchdog thread that writes `sdmc:/blocksmith/hang.txt` naming where the
  main thread was if it ever stops drawing frames.

The Home Menu banner has a real chime, synthesised from sine partials and a
noise burst by `tools/make_banner_audio.py` at package time. That is played by
the Home Menu out of the banner — **the game itself has no audio**.

## Controls

| Input | Does | Rebindable |
|---|---|---|
| D-pad | Move, or move the cursor when the bar is open | yes |
| A | Jump, or take the focused row or slot | yes |
| X | Break block (**hold**) | yes |
| Y | Place block | yes |
| Circle pad | Look, or move the cursor when the bar is open | no |
| L / R | Step hotbar slot, or change tab when the bar is open | no |
| B | Back, close a menu, put down a held stack | no |
| SELECT | Pause menu | no |
| START | Exit the game | no |
| Touch screen | Hotbar, and every tab of the bar | no |

**START closes the game — it does not go back to the title screen.** The row
that returns to the title is **Quit to title** in the SELECT pause menu. Both
save on the way out: the dirty-region flush, the inventory and the player pose
all run on one shared teardown path, so nothing is lost either way.

L and R step the hotbar selection rather than moving you — one slot per
press, wrapping, with a press-then-hold repeat (`source/scene/hotbar.h`).
Render distance is no longer on L/R; it lives on the pause menu's Options
page instead (1 to 3 on an Old 3DS, 1 to 5 on a New 3DS). Up and down
movement exists only in a free-fly build (`-DBS_FLY=1`), which is not what
ships and reads L/R for climbing instead — that build never touches the
hotbar.

Since v1.9.1 the inventory, crafting, chest and furnace screens are not separate
screens any more. They are **tabs on one bar**, and only the tabs that apply are
there — the chest tab exists while a chest is open and not otherwise. L and R
change tab, the D-pad and the circle pad move the cursor, A takes, and B puts
down whatever you are holding before it closes anything.

While the bar is open it owns the pad: the D-pad and circle pad drive the cursor
and stop driving the player, so you cannot walk or turn while sorting your bag.
The pause button is deliberately exempt — a menu that swallowed SELECT could not
be escaped.

Eight actions are rebindable from Options → Controls — the four moves, jump,
break, place and eat — and they may be bound to A, X, Y, a D-pad direction, or
(New 3DS / New 2DS only) ZL or ZR. Eat defaults to ZR; the C-stick is the only
input still unused.

Every row of the table above was read back against the input code on 2026-09-07,
against `source/app/options.h`, `source/app/options.c`, `source/app/input_map.c`,
`source/scene/hotbar.h` and `source/scene/barnav.h`.

## Performance

All figures measured in Azahar. **Azahar does not emulate GPU cost at all**, so
these are CPU-side numbers only, and none of them say what a real console does.

Main-thread cost per frame, measured end to end over an identical world
snapshot restored before each arm, same starting chunk (v1.7.1):

| | median | p95 | p99 | max |
|---|---|---|---|---|
| CPU per frame | 1.799 ms | 2.476 ms | 2.678 ms | 2.905 ms |

Median triangles drawn 16,642. Over-budget mesh frames 11.3%.

**Read those figures as a recorded narrative, not a reproducible artifact.**
They were measured in Azahar during v1.7.1 and written straight into
CHANGELOG.md; no raw log, capture or CSV was ever committed, so nothing in this
repository can reproduce or check them and no later release has re-measured.
Three releases of rendering work have landed since — water's transparent pass,
the 7/8 surface geometry and the crack overlay's extra draw pass — all of which
cost main-thread time these numbers predate.

The chunk vertex pool is held in three tiers of slab so a small chunk does not
claim a large slab, and since 1.8.5 it is **claimed once at startup for the
widest render distance that console will ever be offered**, not at a size fixed
when the game was compiled. If that much linear heap is not there the game says
so at startup rather than misbehaving later.

| Radius | Slabs (16K / 32K / 64K) | Pool |
| --- | --- | --- |
| 3 — an Old 3DS's ceiling | 256 / 120 / 16 | 9,199,616 bytes (8.77 MB) |
| 5 — a New 3DS's ceiling | 256 / 120 / 592 | 46,948,352 bytes (44.77 MB) |

Both figures are **derived by construction, not benchmarked**, from the tier
constants in `source/scene/chunk_render.c`: at radius 3, 256 x 16,384 + 120 x
32,768 + 16 x 65,536 = 9,175,040 plus a 24,576-byte shared index buffer. The
linear heap they come out of is 33,554,432 bytes on an Old 3DS and 67,108,864
on a New 3DS, which is why the ceilings are where they are and not one step
higher (checked 2026-09-01; the arithmetic is gated by a host test that also
proves one radius further does *not* fit).

Whether either console holds 60 fps at its own largest render distance is
**unknown** — nothing here has a GPU and the emulator does not model one, and
radius 5 draws 2.47x the columns radius 3 does.

## Blocks and the atlas

The first eight block ids (`BLOCK_AIR` through `BLOCK_PLANKS`) are a closed
span: `BLOCK_COUNT == 8` is written into every shipped save and every packet, a
`_Static_assert` in `source/world/block.h` holds it there, and it must never
move. Blocks added since — thirty-six more rows, from water and tall grass up
to the furnace and the chest (`BLOCK_CHEST` == 43) — are registry rows above it,
and the registry addresses ids up to `REG_ID_DYN_HI` (0xFD), which is what lets
a server define a block the client did not ship with.

The texture sheet is 16 × 1024 pixels: 64 slots of 16 px, all of them
addressable since v1.8.2 lifted the old 15-slot ceiling. Fifty-eight are painted
— slots 0–57, forty-nine block faces plus nine item icons — slot 63 is
permanently reserved as `ATLAS_TILE_MISSING` — where an out-of-range tile id is
clamped — and the remaining **five, 58–62, are free for the life of the
project**. There is no room to grow past that: 1024 is the PICA200's maximum
texture dimension, so the sheet cannot get taller.

## Building

Requires [devkitPro](https://devkitpro.org/) with devkitARM, libctru and
citro3d. From a devkitPro MSYS2 shell:

```
make
```

To package it as an installable `.cia` afterwards (needs `makerom` and
`bannertool` on PATH, plus a Python 3 for the generated banner assets — the
MSYS2 shell has none, so name one with `BS_PYTHON` instead of editing PATH):

```
BS_PYTHON=/c/Path/To/python.exe tools/make_cia.sh
```

> **Note — run `make deps` once first.** Two things are fetched rather than
> committed, both pinned to an exact commit: libhydrogen (the handshake, shared
> with the server) and `bs_proto.h` (the wire format, which is *defined* in the
> server repo and only mirrored here — committing a second editable copy is how
> the two drift apart). Both land in `deps/`, which is build-fetched and
> disposable.
>
> A build made this way compiles and runs, but Connect reports that no PSK is
> configured: the network pre-shared key is a shared secret and this repository
> is public, so it is supplied on the command line
> (`make cia BS_PSK=<64 hex characters>`) and the `cia` target refuses to package
> without it. The multiplayer server side lives at
> [blocksmith-server](https://github.com/stevenjc2009-byte/blocksmith-server) —
> pinned here as `deps/blocksmith-server` — and is deployed as a Proxmox
> container; its install scripts and systemd units are in that repository, not
> this one.

## Cutting a release

Every release publishes **two** assets, not one:

| Asset | What it is |
|---|---|
| `blocksmith<version>.cia` | the build itself |
| `whatsnew<version>.txt` | the change notes the updater shows on the top screen |

Both are fetched from the same predictable path —
`https://github.com/<owner>/<repo>/releases/download/v<version>/<asset>` — built
from the tag that the `/releases/latest` **302 redirect** names. The two asset
downloads themselves never touch `api.github.com`, which allows only 60
unauthenticated requests an hour per IP and made this updater fail at random
once already.

The version *check* prefers that same redirect for the same reason, but it has
not escaped the rationing — when the redirect cannot be read it still falls back
to `api.github.com` (`source/app/updater.c`). The common path avoids the quota;
the fallback path is subject to it.

### The checklist

1. Cut a branch `v<version>`.
2. Bump `BLOCKSMITH_VERSION` in `source/version.h` and add the release's
   section to `CHANGELOG.md`.
3. Write the change notes: `sh tools/make_whatsnew.sh <version>`.
4. Regenerate the install QR: `python tools/make_qr.py <version>`.
5. **Bring this README up to date, then prove it:**
   `sh tools/check_readme_current.sh`
6. Package: `make clean && make cia BS_PSK=<64 hex characters>`. This writes
   `blocksmith.cia` — the target has no idea what version it is building — so
   copy it to `blocksmith<version>.cia`, which is the name the updater fetches
   and the only name that may be attached to the release. The `make clean` is
   not optional: `make` does not relink on a changed `-D`, so a `make cia`
   after a plain `make` packages a binary built without the key.
7. Boot `blocksmith.3dsx` in Azahar and reach a title screen. Nothing gets
   tagged that has not started.
8. Annotated tag `v<version>`, then publish the GitHub release with both assets.

Step 5 exists because this README went stale across two consecutive releases
while every other asset had a gate and it had none.
`tools/check_readme_current.sh` is pure POSIX shell — no `python`, no
`strings`, both of which are absent from the MSYS2 shell a release is cut from —
and it fails if the version this README names disagrees with `source/version.h`
or the newest `CHANGELOG.md` entry, if any release URL or `.cia` filename in it
points at a different version, if this release's `whatsnew` file is missing, or
if any file path mentioned here no longer exists. It cannot tell whether the
prose is true; that is still a human read.

### Change notes

`sh tools/make_whatsnew.sh <version>` creates `whatsnew<version>.txt` from a template if
it doesn't exist, then checks it against the caps in `source/app/whatsnew.h` —
which it *reads out of that header* rather than repeating, so the checker can't
sign off a file the console would then truncate. The format is two optional
sections, one item per line, plain English, no markdown:

```
[features]
Something new the player can now do.

[fixes]
Something that was broken and now is not.
```

Caps: 4 KB a file, 32 items, 95 characters an item. Anything past a cap is cut
and the screen says so; nothing overruns and nothing is allocated in response to
the file's size.

**A release with no `whatsnew` file still updates perfectly** — the screen says
"No change notes for this version" and the download proceeds. That is by design:
every release published before v1.6.0 is in exactly that position. A timeout, a
404, a malformed file and binary garbage all land in the same place.

## Tests

The world, save format, options, world list, inventory, crafting, water, mining
and UI layout code is all plain C with no `<3ds.h>`, so it is tested on the host
rather than through an emulator:

```
sh tools/run_host_tests.sh
```

One binary per subsystem. One of them parses both
`source/shaders/world.v.pica` and `source/shaders/world_dynamic.v.pica` and
asserts their `uvScale` constants still match `ATLAS_W_PX`/`ATLAS_H_PX` — a
shader file cannot include a C header, and the two drifting apart once made the
entire world render flat brown. The same binary reads `gfx/atlas.png`'s own
IHDR dimensions and proves every addressable tile's rect lies inside the sheet
and shares no texel with any other.

## Status

Playable. **No release since v1.2.5 has been run on real hardware** — every
figure above is from an emulator. Earlier versions did run on a console: the
v1.1.x–v1.2.x GPU-hang bisects were run one arm per boot on a real Old 3DS, and
that is where the freeze they chased was found and fixed. Nothing since has been
back to hardware.
