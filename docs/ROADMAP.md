# Blocksmith roadmap

Every remaining version, in order, with what it adds, changes and fixes.

Two rules run through the whole ladder:

1. **Both consoles, always.** Every version must work on an Old 3DS and a New 3DS.
   Where the two genuinely differ — render distance, clock, cores — it is said
   explicitly. Where they do not, it is not mentioned, because "works on both" is the
   baseline, not a feature.
2. **Nothing borrowed.** Minecraft is a visual reference and nothing more. No assets,
   no textures, no ported code. Art is generated by the scripts in `tools/`. Sound is
   the one exception and only for freely-licensed effects, per an explicit instruction.

## v1.8.4 — New 3DS ✅ released

**Added.** The 804 MHz clock and the L2 cache are asked for at boot. The title's
permissions grant the larger memory mode and the third CPU core. Background work —
world generation, region loading, lighting, saving — moves onto core 2.
*Old 3DS: unchanged, keeps its clock, keeps its work on core 0.*

**Added.** A `RETRY DOWNLOAD` button. A failed download goes straight back to
downloading instead of re-checking the release list first.

**Changed.** You press jump to climb out of water. Walking into the bank keeps you in
the water. A press stays armed for a quarter of a second and buys exactly one climb.

**Fixed.** The core request was written but gated behind a flag that defaults to off,
so a New 3DS got exactly what an Old 3DS got. The two questions are now separate.

## v1.8.5 — Render distance ✅ released

**This is the version that answers "how far can I see".**

**Added.** A higher render distance on a New 3DS. *This is a genuine Old/New split:*
an Old 3DS keeps its current radius, a New 3DS gets a longer one, and the option only
appears on the console that can hold it.

**Changed — the chunk mesh pool is sized at runtime** from the detected console, instead
of at compile time for the smaller one. This is the change the whole version rests on:
the pool costs **9,199,616 bytes at radius 3 and 46,948,352 at radius 5**, and an Old 3DS
has a 33,554,432-byte linear heap, so raising the ceiling before the pool became runtime
would simply have stopped an Old 3DS booting. The two ceilings are gated by a host test
that also proves one radius further does *not* fit, so 5 is a measurement rather than a
preference.

**Not changed — the world budget, and this is deliberate.** The plan was to make it
runtime too. Measuring it said not to, on four counts. The world store is `malloc`, on the
**application** heap; the mesh pool is `linearAlloc`. **They never competed**, so the
scenario that motivated the change does not exist. `WORLD_BUDGET_BYTES` allocates nothing
at all — it is a refusal threshold, three scalars and a compare-and-swap — so a per-console
value would save an Old 3DS exactly zero bytes. Lowering it to an Old 3DS's own ceiling
would swap a 2.34× margin for a 1.00× fit on the one failure it exists to prevent, and a
refused claim is a permanent hole in the terrain, not a dropped frame. And `budgetClaim`
tests `bytes > WORLD_BUDGET_BYTES - used`, which **wraps** the moment the cap becomes a
variable that can drop below `used` — buying a new silent failure for no gain.

The measurement did find a real error, in the comment justifying the 12 MB cap. Its
"17×17 ≈ 9.25 MB" was v1.4.x arithmetic that counted block data only, omitting both the
chunk headers and the 32 KiB light column now carried on **every** column on **both**
models. The true figure is **18,972,272 bytes** — a 2× understatement, for a case that
would not have fitted the cap it was being used to justify. Per-column cost was compiled
for ARM and read out of the emitted constants rather than derived, which is how the chunk
header turned out to be **8 bytes and not 12**: the ARM EABI defaults to `-fshort-enums`.
The 12 MB cap holds radius 5 at 88.7% and refuses radius 6 — very nearly the right ceiling,
by accident rather than design. It stays, now with a derivation that is true.

**Changed — the fog, which was the other half of the ceiling.** Render distance was never
only a memory problem. The old fade was a PICA200 hardware LUT: 128 entries indexed by
1/w, whose knots bunch towards the camera, so with the near plane pinned the first knot
past the far plane sat at 20.68 blocks and everything beyond it was a single unshapeable
segment. That capped half-visibility at about 14.4 blocks **at any radius** — measured
14.3358 / 14.3651 / 14.4065 at radius 3 / 4 / 5, so widening the ring bought 0.20% and a
New 3DS would have paid for 121 columns it could not see through. The fade now comes from
a ramp texture sampled through a TexEnv stage off linear eye depth carried in a second
texture coordinate. Half-visibility becomes **28.5 blocks at radius 3 and 47.5 at radius
5** — linear at 9.5 blocks per step, against 0.03 before.

**Added.** A boot probe that prints the real free-memory figure on the console it is
running on. Every memory number in this project is currently arithmetic on paper; the
only hardware reading on record is from before v1.7.0 and is for an Old 3DS.

**Fixed — the pending network-edit store.** It took a flat 1.02 MB whether or not you
ever opened Multiplayer. It is now allocated on the first server packet that needs it and
given back when you leave a session, so single player never pays it. **Measured off the
built ELF, not estimated: `.bss` 1,725,944 → 660,968 bytes, a reclaim of 1,064,976.**

**Corrected 2026-09-01.** This entry also used to claim the GPU preflight scratch cost
512 KB on every boot, and that the two together were 6.5% of everything the game
allocates. **The GPU half of that was wrong.** All of `app/gputest.c` sits inside
`#if BS_GPU_TESTS`, which `app/gputest.h:37` defaults to 0, so a shipping build never
allocated those bytes at all — compiled both ways under devkitARM, `=0` yields an 1,832 B
object with an empty symbol table against 88,832 B at `=1`. The buffers are now freed
after the batteries that use them anyway, which helps a diagnostic build and helps the
shipping build by exactly nothing. **The 1.02 MB above is the whole of the real reclaim.**

## v1.8.6 — Speed ✅ released

**Rewritten 2026-09-01, from measurement.** This entry used to list eight optimisations.
Five of them were wrong, and they were wrong in a way that would have spent the whole
version on work with no effect. What follows is what survived being measured. Every
number below is host x86-64 against the real project translation units unless it says
otherwise; the game runs on a 268 MHz ARM11 or an 804 MHz one, so a host figure is a
ratio, never a frame cost.

**Fixed — three quarters of the tree pass is thrown away after it is computed.** This is
the version's first job because it is the largest confirmed win and the only one that can
be proved exactly. `worldgenDecorate` (`world/worldgen.c:495-498`) scans tree cells out
past the column being decorated, and `treeInCell` asks the generator for terrain height at
`:348` *before* anything checks whether the tree can reach. `treePut` then discards the
whole tree with a bounds test. Classified across 8,273 queries over 900 columns:
**75.3% are for a tree that cannot place a single block in the column being generated.**
A horizontal-reach reject before the height query wins about **6.6% of column generation**,
or 7.6% with the in-column cache as well.

It is also the safest change in the version, because `treePut` already discards exactly
these trees: **the generated world must come out byte-identical**, so the acceptance test
is an exact before-and-after comparison of generated columns, not a timing that could be
argued with. In game, the figure that should move is `LOAD_STAGE_GENERATE`, already timed
at `app/worker.c:270-273`.

*The old entry claimed one height query costs ~476 noise evaluations against ~2,975 for a
whole column. Measured over 1,271 columns and 6 seeds: **208** for a query and **24,204**
for a column. A single query is a seventh as expensive as claimed, and the win comes from
how many of them are pointless, not from how dear each one is.*

**Changed — the New 3DS work budgets, but not the knob the old entry named.**
`main.c:192-193` and `:238-239` are untouched by any `hwIsNew3ds()` branch, so that half
was right. The correction: `svcGetSystemTick` runs at the fixed nominal rate whatever
`osSetSpeedupEnable` is doing (`app/hw.h:32-42`, citing libctru), **so a millisecond is a
millisecond on both consoles and raising the millisecond budgets achieves nothing.** On a
New 3DS the drains finish their 3 chunks and 4 columns in roughly a third of the wall time
and then stop on the *count* cap with budget left unspent. The knob is `DRAIN_MAX_CHUNKS`
and `RELIGHT_MAX_COLUMNS`, New 3DS only. To be measured before it is changed — `frames.csv`
already carries `built`, `mesh_ms` and `meshq`, and the proof is `built` pinned at 3 with
`mesh_ms` well under 4.0 and `meshq` elevated. If `mesh_ms` is near 4.0 there is nothing
here to win.

**Added — a real look at column generation itself.** `wgdColumn` is **91%** of the cost of
generating a column: 22,031 noise evaluations and 1.25 ms against the 24,204 and 1.379 ms
for everything. The entire tree pass above is the other 9%. No candidate on the original
list touched it, and it is where a serious worldgen win would have to come from.

**Fixed — a test that does not test what it appears to.** `interact_test.c` never calls
`lightEngineInit(true)`, so `lightEnabled()` is false for the whole binary and the relight
paths at `scene/interact.c:114` and `:308` never execute in it. That is true today
independently of anything else in this version.

### Removed from this version, with the evidence that removed them

- **Nearest-first chunk ordering.** The ordering claim was correct — raster scan into a
  strict FIFO (`main.c:849-861`, `world/jobq.c:25-33`), and your own column really is the
  41st of 81 at radius 3, which `worker.c:139` already says. But `main.c:1541` sets
  `.ring_ready = in >= total` and `scene/loading.c:91` exits only when the *whole* ring is
  in, so **reordering the queue cannot shorten the loading screen by a single frame** — the
  work is identical and the exit condition is a conjunction over all of it. During play,
  `genRecenter` queues only the new edge strip, which sits a full column beyond the drawn
  boundary where the fog is opaque anyway. There is a version of this worth doing, but it
  means starting play with an unmeshed periphery, and that is a design decision rather than
  an optimisation.
- **Coalescing the local-edit relight.** The premise was backwards. `relightq` is fed only
  by remote edits and water; **a local break or place calls `lightRelightColumn`
  synchronously in single player and multiplayer alike**, so there is no gap between the two
  paths to close. Measured cost of one call: median 0.107 ms, p95 0.175 ms, max 0.196 ms
  over 200 calls. Coalescing would trade deliberate same-frame light correctness for
  smoothing a spike that is not there.
- **Per-file `-O3`.** `Makefile:58` is already `-O3` globally, with the measurement that put
  it there recorded at `:47-51`. There is no `-O2` to raise, and a per-file override already
  exists and is already used.
- **Crafting recipe matching.** `RECIPE_COUNT` is 4 and `craftCanMake`/`craftMake` take a
  direct index — there is no table walk. The only loop over recipes draws the inventory
  screen and never runs in the gameplay frame.
- **Camera and player trigonometry, and the per-frame projection matrix.** Both real, both
  microseconds, on a thread this project's own measurements put at GPU-blocked for roughly
  15.7 of every 16.71 ms. **Provenance, corrected 2026-09-03 (v1.8.17): measured, not a GPU
  reading** — this is Azahar frame-time minus known CPU cost, not a GPU-busy sample; Azahar
  has no GPU cost model and its `C3D_GetDrawingTime()` returns a constant 0.249 ms, so
  "GPU-blocked" is an inference from the CPU side, not a reading of the GPU. See
  `source/debug/metrics.h:132`. A real GPU-blocked figure would require hardware profiling on
  console, which this project does not yet have. The specific pair originally cited cannot
  even coexist — that camera code is dead in a shipping build, though not for the reason
  first written here.
  **Corrected 2026-09-03:** the guard immediately around it is `#if BS_ORBIT`
  (`camera.c:102`), not `BS_FLY`. The conclusion survives, because the whole `cameraUpdate()`
  call is itself gated by `#if BS_FLY` at `main.c:4994`, which defaults off — so it is dead
  via the OUTER gate, not the inner one. Worth correcting because "it is inside `#if BS_FLY`"
  sends the next reader to the wrong line to check the claim, finds a different macro, and
  has no way to tell whether the entry or the code moved.

  A genuine 4-transcendental residue existed between `player.c` and `interact.c:339-342`.
  **Half of it is now gone:** `player.c` asked for `sinf(yaw)` and `cosf(yaw)` twice each and
  as of 2026-09-03 asks once each. Folded despite this entry's own "not worth the version's
  attention", because it was free and provably exact rather than merely close — 16,000,025
  sampled yaw values, zero bit differences, with a red control (negation dropped) catching
  2,001. The `interact.c` half is untouched and remains not worth a review cycle on its own.

## v1.8.7 — Terrain ✅ released

**Corrected 2026-09-01. This entry used to say "the version that adds the Beta 1.7.3
world". That was wrong, and it was wrong against code that had already shipped.**

The Beta 1.7.3 world is already here. It is not future work:

- `world/genversion.h:104` stamps every new world `GEN_VERSION_FOR_NEW_WORLDS`, which
  is `GEN_VERSION_BIOME` (3), and the density field is `version >= GEN_VERSION_DENSITY`
  (2). So every new world already gets it. The density generator shipped in v1.7.0 and
  biome identity in v1.8.3 — both *earlier* than this entry.
- The lattice is Beta's own. `world/worldgen_density.h:64-73` is 5×5×17 sample points
  at 4 blocks horizontally and 8 vertically; Beta's documented grid is 5×5×17. The
  world is 128 tall (`world/world.h:23-24`) with sea at 64 — Beta's height and Beta's
  sea level.
- Overhangs are already occurring, and were measured rather than hoped for. An overhang
  needs the density field to rise by more than 8 blocks across one vertical cell. At the
  old amplitude table the best any test seed managed was −2.68 blocks, meaning no
  overhang was geometrically possible anywhere. At the shipped table a mountainous seed
  reaches **+16.76 blocks, with 9.99% of all lattice steps rising**
  (`world/worldgen_density.c:130-141`).

**What this version is instead: making it good on every seed, not on two.**

**Changed — amplitude tuning across a real seed sweep.** The per-biome amplitude table
(`worldgen_density.c:70-151`) was, by its own comment, "tuned by eye against the terrain
it produces", and the overhang measurement above rests on exactly two seeds. Nothing
here can crash or corrupt a world; the risk is entirely that "feels like Beta" is being
hit inconsistently. The fix is a sweep wide enough to state an overhang rate per biome
with a real distribution behind it, not a figure from one lucky seed.

**Added — a console timing reading for column generation.** There is no ARM11
measurement of the density generator anywhere in the tree. Every cost figure on record
is host x86-64 (1.055–1.310 ms/column against legacy's 0.757–0.804, a 1.37–1.64×
multiplier). That gap is not specific to this version — it already applies to every new
world a player starts today — but this is where it gets closed, because v1.8.6 lands
immediately before it and needs the same instrument.

**Not changed: the world height.** 128 already matches Beta, and the code's own
measurement says amplitude, not height, is the overhang lever. Going taller is also not
free — by a much wider margin than this paragraph claimed when it was first written.

Corrected 2026-09-01, second pass. The original text quoted a 17×17 worst case of
"~9.25 MB" and derived "~13.9 MB" for a 192-block world from it. That 9.25 MB is the
figure the v1.8.5 section of this same document retracts as a 2× understatement, and
`world/budget.h:26-31` retracts it too: it counted block data only, omitting both the
per-chunk header and the 32 KiB `LightColumn` that has hung off every loaded column
since v1.5.0. Deriving from a retracted number produced a retracted answer.

The real arithmetic, from `world/budget.h:24-68` (compiled for ARM and read out of the
emitted constants, not derived on paper): one loaded column is **65,648 B** — 48 B of
`Column`, 32,832 B of chunks (8 × an 8-byte header plus 4,096 cells) and a 32,768 B
`LightColumn`. Everything but the 48 B struct scales with height, so at 192 blocks a
column costs ~98,464 B, and the 17×17 case — render radius 7, plus the worker's one
staging column — reaches **~28,554,560 B against a 12 MB cap** (`world/budget.h:75`).
That is **~2.27×** the cap, not the 1.16× the old figure implied.

The conclusion does not change, it only stops being marginal: 192 does not fit, and no
plausible trimming makes it fit. Still straight-line arithmetic rather than a
measurement — but arithmetic on the figure the compiler produced, not on a retracted one.

Full research, with sources and file:line evidence: `docs/research/terrain-beta-1.7.3.md`.

## v1.8.8 — Biome identity ✅ released

**Changed — colour comes from tint, not from blocks.** This is Minecraft's own
approach and it is the right one here: there is no separate block for desert dirt or
swamp grass. One block, tinted by the biome it sits in, from a climate colormap read
by temperature and rainfall. It costs nothing per biome, where a block per biome costs
an ID, atlas space, and a lockstep change on the server every time.

**Added — real per-biome blocks** where the block genuinely differs rather than merely
looking different: wood, leaves, planks, and the ground cover that is actually a
different material.

**Added — plant variety.** Short grass, two-block tall grass, ferns, and flowers. These
*do* get their own blocks, because the difference is shape, not colour. Grass strands
are recoloured to match the grass block they grow from.

**Added — flowers, placed on purpose.** Poppies and the rest, biome-specific rather
than scattered everywhere, so that a dedicated flower-field biome later actually means
something.

**Added.** Apples drop from leaves, and can be picked up and eaten.

**Changed.** Dead bushes redone.

**Fixed.** Cactus cannot currently be broken. Every new block in this version ships
with its own durability, and that is checked, not assumed.

**Added — debug menu only, never a game feature:**
- the current biome on the bottom-screen readout
- a neon biome-border toggle
- a block list: every block in the game with its icon and name, on the **bottom**
  screen

**Groundwork.** The block ID ceiling is lifted, client and server in lockstep. Nearly
everything below this line needs it.

## v1.8.9 — Sky and weather ✅ released

**Changed.** The day/night cycle and the sun's movement, matched to Minecraft's
timings and light curve.

**Added — weather that knows where it is.** Rain and snow are decided by biome
temperature the way Minecraft decides them: above a threshold it rains, below it
snows, deserts and savannas get neither, and altitude cools the air as you climb.

**Added — snow that settles in layers**, up to **exactly one block deep and no
further**. That is vanilla's own rule, not a compromise: the accumulation limit
defaults to one layer and only a changed game rule raises it. There will be no towers
of snow.

## v1.8.17 — New 3DS, in earnest ✅ released

**In flight, not committed as written.** This is being built right now, across parallel
work, so treat everything below as scope rather than fact — no part of it is verified, and
thread placement specifically cannot be tested without real hardware. The 804 MHz clock and
L2 cache were switched on for a New 3DS back in v1.8.4, but almost nothing downstream of
that request was ever gated on `hwIsNew3ds()`, so a New 3DS has been doing the same
per-frame work as an Old one ever since. This version's job is to actually spend the extra
RAM, CPU speed and L2 cache a New 3DS already has.

**Planned.** Per-frame work budgets — the mesh drain, the relight pass, the loading-screen
drain in `source/main.c` — gated per console instead of flat constants. The New-3DS render
distance default raised from 2 toward the ceiling of 5 v1.8.5 already granted, and
`WORLD_BUDGET_BYTES` (12 MB, flat and ungated today) raised on New, where roughly 29 MB of
application heap currently goes unspent. Thread placement spread across the cores a New
3DS is actually granted, instead of using two of its four.

**Planned — fixed.** Breaking a furnace drops its contents instead of destroying them
silently, and a burning furnace shows its lit front face — both carried over from v1.8.15.
The water-entry splash moves from the player's feet to the water surface, plus a new splash
on leaving the water and a wake while swimming at the surface.

**Planned — added.** Per-biome dirt colour, by tint — the one item still missing from the
per-biome materials list v1.8.8 otherwise completed.

## v1.8.20 — Time, unplanned ✅ released

**Not a roadmap version.** Inserted between v1.8.19 and v1.9.0 by the multiplayer audit that
followed "Sound", which found the day/night clock had never been synchronised: every client
ran its own counter from its own join time, so two players in one world could be hours apart.

**Added.** `BS_APP_TIME_SYNC` (`0x10`, server-to-client only, one `uint64` little-endian),
sent on join and once a second after. Weather rode along free, because `weatherAt()` is a
pure function of the tick and the seed and both were already agreed. The server persists the
counter so a restart does not rewind everyone to dawn.

This entry exists so a later reader does not go looking for a plan item that explains the

## v1.9.0 — Storage and quality of life

**Added.** Chests. Stack splitting and merging, shift-move, and the small conveniences
that a game gets tiring without.

---

## v1.9.1 — The new interface

**Changed.** The menus and inventory redrawn around a long horizontal bar of options —
the shape the legacy console crafting menu and the PS3 system menu share. Referenced,
not copied: none of their art, none of their layout metrics, none of their icons.

---

## v1.9.2 — Redstone

**Added.** Wire, power, levers, buttons, pressure plates, doors, pistons.

---

## v1.9.3 — The other worlds

**Added.** Two more dimensions with their own names — the fire one and the end one —
each with its own generator, its own blocks and its own way in.

**Candidates for later**, since more were asked for: a shattered sky dimension of
floating islands reached by falling; a frozen deep reached from a cave; a mirrored
version of the overworld where it is always night.
