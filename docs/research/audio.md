# Audio — research brief for Blocksmith v1.8.17 "Sound"

Scope note: this is research and planning only. **Nothing in the Blocksmith project tree was
changed.** `source/`, `docs/`, `tools/` and `README.md` were read, never written. No audio
files were downloaded — this brief names candidate sources and states their licence terms; it
does not fetch anything from them.

Provenance is marked throughout. Unmarked claims carry an inline source link. Otherwise:

- **[COMPUTED]** — I ran the cited formula/arithmetic myself and this is the output. The script
  is in the session scratchpad (`audio_ram_budget.py`); it is throwaway, not part of the repo.
- **[DERIVED]** — arithmetic on top of cited or measured numbers, shown so you can check it.
- **[INFERENCE]** — my engineering judgement. Not sourced.
- **[NO SOURCE]** — I looked and could not find one. Named explicitly so it is never implemented
  as if it were a fact.

The owner's instruction that scopes this whole brief, verbatim: *"grab some sound effects that
are free to use licensing wise."* Licensing is therefore the load-bearing part of Part B, not a
footnote — a wrong reading there is the expensive-later kind of mistake.

**Hard constraint, stated up front and never revisited below: nothing borrowed from Minecraft or
Nintendo, ever, regardless of host.** No ripped game audio. Every source considered in Part B is
either an original-recording library or a synthesis tool; none of them are ROM rips, and none
are recommended here.

**The most important framing point, and it changes what this brief has to argue for.** The
project has already decided this fight, in writing, before this brief existed.
`docs/ROADMAP.md:11-13`:

> **Nothing borrowed.** Minecraft is a visual reference and nothing more. No assets, no
> textures, no ported code. Art is generated by the scripts in `tools/`. **Sound is the one
> exception and only for freely-licensed effects, per an explicit instruction.**

and `docs/ROADMAP.md:355-359`, the v1.8.17 entry itself:

> **Added.** A real audio system — footsteps that know what you are walking on, block breaking
> and placing per material, animals, water, ambience. **Effects sourced under licences that
> permit any use, credited in the repository.**

So this is not a debate about whether Blocksmith breaks its own "everything is generated from
scratch" rule (`README.md:8-13`: *"No Minecraft assets, no ported code, no third-party texture
pack — every block texture, the font, the Home Menu art and the banner chime are generated by
the scripts in `tools/`"*). The roadmap already carved out the one named exception, in the same
sentence that states the rule. Part D still lays out a synthesis option for the sounds that are
cheap to synthesise, because the project has working prior art for it (`tools/make_banner_audio.py`,
see D-equivalent material in Part D) — but sourcing under a free licence is the *authorised* path,
not a workaround.

# Part A — The 3DS audio reality

## A1. There is no audio subsystem in the tree today — confirmed

A full-tree search for `ndsp`, `NDSP`, `csnd`, `CSND`, `audio`, `sound`, `.wav`, `dspfirm`,
`DSP_` and `ndspChn` under `source/` returns no real hits — the handful of matches on the word
"sound" are all in comments about *reasoning* ("sound logic", "a sound argument"), never about
the audio hardware. `source/main.c` has no audio-related stub, TODO or dead code path.

**[CONFIRMED, from the tree]** `README.md:96-98` says this in as many words:

> The Home Menu banner has a real chime, synthesised from sine partials and a noise burst by
> `tools/make_banner_audio.py` at package time. That is played by the Home Menu out of the
> banner — **the game itself has no audio.**

That chime is the *only* audio artefact anywhere in the project, and it is explicit in its own
header comment (`tools/make_banner_audio.py:14-16`) that it is out of scope for the game's own
audio system: *"this track is played by the 3DS Home Menu out of the banner, NOT by Blocksmith.
It needs no ndsp, no audio engine and nothing from roadmap task 43."* So v1.8.17 is building on
a genuinely empty slate: no channel management, no mixer, no format loader, no romfs audio
folder (`romfs/` presently holds only `cacert.pem`), nothing. Everything in this brief is new
work, not a wire-up of something half-built.

## A2. What libctru's NDSP actually offers

The 3DS's audio hardware is a dedicated **CEVA TeakLite II DSP at 134 MHz**, exposed to homebrew
through the high-level `ndsp` service in libctru rather than through raw DSP programming
([GBATEK 3DS Sound and Microphone](http://problemkaputt.de/gbatek-3ds-sound-and-microphone.htm),
corroborated by 3dbrew's hardware description surfaced in search: *"CEVA TeakLite. 134Mhz. 24ch
32728Hz sampling rates."*).

**Channels.** NDSP exposes **24 mixing channels**, indexed 0..23
([`ndsp/channel.h`](https://github.com/devkitPro/libctru/blob/master/libctru/include/3ds/ndsp/channel.h)
— every per-channel function, e.g. `ndspChnSetRate(int id, float rate)`, documents the id range
as 0..23). Each channel carries its own rate, format, interpolation mode and a **12-slot mix
array** (front L/R, back L/R, then the same four repeated for two auxiliary outputs) — more
routing flexibility than a stereo 3DS speaker pair needs, but the slot count is free.

**Formats.** Three encodings, each available mono, and PCM8/PCM16 also available interleaved
stereo: `NDSP_FORMAT_MONO_PCM8`, `NDSP_FORMAT_MONO_PCM16`, `NDSP_FORMAT_MONO_ADPCM`,
`NDSP_FORMAT_STEREO_PCM8`, `NDSP_FORMAT_STEREO_PCM16`
([`ndsp/channel.h`](https://github.com/devkitPro/libctru/blob/master/libctru/include/3ds/ndsp/channel.h)).
**The `ADPCM` encoding is not a 3DS-specific codec — it is literally Nintendo's GameCube/Wii
DSP-ADPCM format**, reused verbatim; the header's own comment on the enum value reads *"DSPADPCM
(GameCube format)."* That matters for tooling: existing open-source GameCube encoders —
[`Thealexbarney/gc-dspadpcm-encode`](https://github.com/Thealexbarney/gc-dspadpcm-encode) and
[`Thealexbarney/DspTool`](https://github.com/Thealexbarney/DspTool) — produce byte-compatible
data, so nothing 3DS-specific has to be written to get ADPCM compression; see Part D.

**Sample rate.** `ndspChnSetRate` takes a free `float`, not an enum — any rate is legal at the
API level. The DSP's own **native mix rate is ~32728.5 Hz** (`CLOCK/1024` on the DS-derived
clock, not a clean 32768), and it resamples every channel to that rate regardless of what you
set. **[NO SOURCE]** for a hard minimum/maximum accepted by `ndspChnSetRate` — nothing in the
header states one, and homebrew examples use everything from 8 kHz to 48 kHz without incident.
**[INFERENCE]** Because the DSP always resamples, there is no correctness reason to author sound
effects at exactly 32728.5 Hz; matching it only avoids one extra resampling pass, which is not
worth the readability cost of an ugly constant for one-shot SFX. It would matter more for a
looping BGM track meant to loop sample-accurately, which v1.8.17's scope (footsteps, breaking,
placing, animals, water, ambience — no music is named) does not include.

**Streaming.** libctru ships an official streaming example
([`3ds-examples/audio/streaming/source/main.c`](https://github.com/devkitPro/3ds-examples/blob/master/audio/streaming/source/main.c))
showing the standard pattern: a background thread decodes into a small ring of wave buffers and
hands each to `ndspChnWaveBufAdd` as the previous one finishes. **[NO SOURCE, flagged as a real
risk]** An open devkitPro issue records that the DSP-backed examples in that same repository
(`streaming`, `filter`, `opus-decoding`) currently produce **no sound at all** on some toolchain
versions, while only the CSND-based `mic` example works
([devkitPro/3ds-examples#36](https://github.com/devkitPro/3ds-examples/issues/36)). This does
not mean NDSP itself is broken — many shipped homebrew titles use it successfully — but it means
**the official example code cannot currently be trusted to compile-and-run as a starting point
without local verification first**, and that verification (a five-second beep on real hardware,
per the workflow rules) should be the very first step of implementation, not an afterthought.

## A3. The DSP firmware requirement — and what it means for a CIA specifically

**The DSP service will not function without a real firmware binary present at
`sdmc:/3ds/dspfirm.cdc`.** This is Nintendo's own copyrighted DSP firmware image, and libctru
cannot ship it. Without the file, `ndspInit()` fails and nothing plays — multiple independent
homebrew guides state this in the same words: *"Homebrew requires a copy of the DSP firmware to
be present at sdmc:/3ds/dspfirm.cdc"* ([GameBrew: DSP Firmware Dumper](https://www.gamebrew.org/wiki/DSP_Firmware_Dumper_3DS),
[3DS Hacks Guide troubleshooting](https://3ds.hacks.guide/troubleshooting.html)).

**How a user gets it, on real hardware.** The standard modern path is one menu action, not a
separate homebrew app: Luma3DS (the custom firmware essentially every 3DS homebrew user runs)
added a built-in dumper in **Rosalina → Miscellaneous options → Dump DSP firmware**, which pulls
the firmware out of whatever official title last used the DSP and writes it to the SD card once
([GameBrew: DSP Dump 3DS](https://www.gamebrew.org/wiki/DSP_Dump_3DS)). This has to be done
**once per SD card**, not once per homebrew app — after that, every DSP-using homebrew title
just works.

**What this means for distribution, precisely, and where the project's own memory already has
the sharp edge of this.** Two cases:

- **A 3DSX launched from the Homebrew Launcher never needed the dump at all** — that path has
  never required it, per direct community correction of the more common claim
  ([GBAtemp: "3dsx homebrew never needed a dsp dump"](https://gbatemp.net/threads/n3ds-dspdump-guide-error.460721/)).
- **A CIA — which is how Blocksmith ships, per the project's own release convention of a
  `modelkit<version>.cia` / `hotswap`-style CIA on GitHub Releases — does need the dump.** This
  is stated for another CIA-shipping homebrew project in the same words: *"the CIA format
  requires a DSP binary dump saved on your SD card as /3ds/dspfirm.cdc, and this is not an
  optional step"* ([ScummVM 3DS port docs](https://docs.scummvm.org/en/v2026.2.0/other_platforms/nintendo_3ds.html)).

**So: a user who has never dumped DSP firmware, installs the Blocksmith CIA, and has audio
turned on, gets silence — not a crash, silence — unless the game checks for the file and either
warns or degrades gracefully.** That check is new work v1.8.17 has to include; nothing in the
tree does it today (A1). **[INFERENCE]** The cheapest correct behaviour is: attempt `ndspInit()`,
and if it fails, fall back to a "no audio" mode with **no visible error and no crash** — the game
already ships and plays correctly with zero audio (that is the entire current state), so the
fallback is "behave exactly as v1.8.16 did," not a new degraded mode that needs its own design.

**Emulators are the opposite case, and it matters for testing.** Azahar/Citra emulate the DSP in
**software (HLE)** by default and do not need a real dump at all — *"a 0 byte file is sufficient
for homebrew audio to work since Citra uses HLE"*
([devkitPro/3ds-examples audio/README.md](https://github.com/devkitPro/3ds-examples/blob/master/audio/README.md)).
**This is a real trap for this project's own testing workflow specifically**: the project's
memory notes record that Azahar is the emulator used for automated verification. Audio that
plays correctly under Azahar's HLE proves only that the *mixing and format logic* works — it
proves nothing about the real DSP firmware path, the `dspfirm.cdc`-missing fallback, or the
handful of documented HLE-only bugs (crackling on volume changes, stutter under many
simultaneous SFX — [Azahar #766](https://github.com/azahar-emu/azahar/issues/766) and the
Azahar changelog). **A hardware playtest is not optional for this version**, and specifically a
hardware playtest on an SD card that has **never had `dspfirm.cdc` dumped**, to prove the silent
fallback in the paragraph above actually stays silent rather than crashing or hanging.

## A4. RAM cost — this is not where the version's risk lives

**[COMPUTED]**, from `audio_ram_budget.py` in the scratchpad. A single mono PCM16 clip at a
typical sound-effect length and rate:

| Duration | 11025 Hz | 16000 Hz | 22050 Hz |
|---|---|---|---|
| 0.15 s | 3.2 KiB | 4.7 KiB | 6.5 KiB |
| 0.30 s | 6.5 KiB | 9.4 KiB | 12.9 KiB |
| 0.50 s | 10.8 KiB | 15.6 KiB | 21.5 KiB |

For a realistic library — Part C lands on roughly 35-50 distinct clips — at an average 0.4 s and
22050 Hz mono PCM16, **[COMPUTED]**:

| N clips | Resident, PCM16 | Resident, DSP-ADPCM (~3.6:1, A2) |
|---|---|---|
| 20 | 0.34 MiB | 0.09 MiB |
| 40 | 0.67 MiB | 0.19 MiB |
| 60 | 1.01 MiB | 0.28 MiB |
| 100 | 1.68 MiB | 0.47 MiB |

**Set that against the real linear-heap numbers, read directly out of the tree
(`source/scene/render_dist.h:99-113`, measured off booted hardware, not computed):**

| Console @ render radius | Linear heap | Free after boot | Mesh pool + GPU buffers | **Remaining headroom** |
|---|---|---|---|---|
| Old 3DS @ 3 (its only radius, per `render_dist.h:120-124`) | 33,554,432 B | 22,479,872 B | 11,074,560 B | **[DERIVED] 11,405,312 B ≈ 10.88 MiB** |
| New 3DS @ 5 (its ceiling) | 67,108,864 B | 56,034,304 B | 48,823,296 B | **[DERIVED] 7,211,008 B ≈ 6.88 MiB** |
| New 3DS @ 4 | 67,108,864 B | 56,034,304 B | 27,851,776 B | **[DERIVED] 28,182,528 B ≈ 26.88 MiB** |

**The surprising number here is the middle row.** A New 3DS running at its own maximum render
radius has *less* linear-heap headroom left over than an Old 3DS does at radius 3 — 6.88 MiB
against 10.88 MiB — because the mesh pool at radius 5 (46.9 MB) eats more than the extra 32 MB
of New-3DS heap gives back. **A full resident SFX library, even at the uncompressed PCM16 end of
the table above, is under 2 MiB — 18-24% of the tightest of these budgets, not a dominant cost.**
Audio is not what will make radius 5 fail to fit; it is a small, boundable addition on top of a
number the project has already measured and tested against
(`tests/mesh_pool_bytes_test.c`, per `render_dist.h:116-118`).

**Streaming music is a different question, and the answer depends entirely on what "resident"
means.** A naive full-track load as raw stereo PCM16 at CD quality is **[COMPUTED] ~10.1 MiB per
minute** — enough on its own to blow the New-3DS-at-radius-5 headroom in under 41 seconds of
music. But nothing requires loading a whole track: the standard NDSP streaming pattern (A2) only
ever holds a **small ring of short buffers** resident — **[COMPUTED]** two 1-second mono PCM16
buffers at 22050 Hz cost **86 KiB total**, decoded from disk/romfs a chunk at a time. **The
constraint on streaming is therefore not linear-heap RAM at all — it is (a) CPU time for the
decoder, competing with the mesher and the ARM11's lack of a hardware divide, and (b) the
`dspfirm.cdc` question in A3 applying identically to music as to SFX.** v1.8.17's roadmap
wording — "footsteps... block breaking and placing... animals, water, ambience" — **names no
music track**, so this brief treats streaming BGM as **out of scope for v1.8.17** and flags it
only so a future version does not assume it is free because the SFX budget was.

# Part B — The licence landscape

This is the part the owner's instruction makes load-bearing. Read every row before picking a
source; the differences are not cosmetic.

## B1. The three licence families, precisely — read this before B2

**CC0 ("public domain dedication").** The rights holder waives copyright entirely, to the
maximum extent the law allows. **No attribution required, ever, for any use, commercial or
not.** This is the only one of the three with zero ongoing obligation. Freesound's own community
guidance states it plainly: *"CC0 imposes (almost) no restrictions nor requirements and you can
use those sounds as you see fit"* ([Freesound FAQ](https://freesound.org/help/faq/)).

**CC-BY ("Attribution").** Free to use, including commercially and including inside a compiled,
closed-source binary, **on the condition that the work is credited**. The standard citation is
title, author, source URL and licence
([Freesound forum guidance](https://freesound.org/forum/legal-help-and-attribution-questions/39864/)).
Crucially: **attribution does not have to be in-game or in a splash screen.** A credits file
shipped alongside the release — a `CREDITS.md`, a section of the README, a line in the GitHub
Release notes — satisfies the letter of every CC-BY licence encountered in this brief; nothing
requires it to appear at runtime. For Blocksmith specifically, this is cheap: the project already
maintains a public GitHub repo with release notes per version (per the project's own release
workflow), so a `CREDITS.md` entry per sourced clip is a small, mechanical addition to a process
that already exists.

**CC-BY-SA ("Attribution-ShareAlike") — flagged as the one that needs a real decision, not a
skim.** Same attribution requirement as CC-BY, **plus** a "share-alike" clause: any work you
create that is *itself a derivative* of the CC-BY-SA asset must be released under the same
licence. **The viral question is whether "a game that contains the sound" counts as a derivative
of the sound, or only a remix/edit of the sound file itself does.** The community consensus,
including from OpenGameArt's own forum (the site that hosts the most CC-BY-SA game audio), is
that **it does not extend to the whole game** — *"the general understanding is that a game using
the artwork is not itself a derivative work, so you only need to give attribution... share-alike
requires that any derivative work you make using a CC BY-SA track must also be released under CC
BY-SA, but for most games it has no effect"*
([OpenGameArt forum: "About CC-SA"](https://opengameart.org/forumtopic/about-cc-sa); consensus
summarised across [itch.io threads](https://itch.io/post/635417) referenced in the same search).
**But this is consensus, not settled law** — Creative Commons' own FAQ lists *"syncing sound to a
video"* as an example qualifying adaptation, and at least one forum participant switched their
own project away from CC-BY-SA specifically over this ambiguity after "giving up" trying to
resolve it. **[INFERENCE] Recommendation: treat any CC-BY-SA clip that is used unmodified as
safe (matches consensus), but do not encode, filter, resample-for-pitch-variation, or otherwise
transform a CC-BY-SA source clip without re-checking, since a transformed clip is unambiguously a
derivative** and Part D's pipeline (which does resample every clip to the project's target rate)
would trigger exactly that ambiguity if a CC-BY-SA source were fed through it. **The clean
resolution is simpler than adjudicating the ambiguity: prefer CC0 and CC-BY sources over
CC-BY-SA wherever an equivalent sound exists, and use CC-BY-SA only when nothing else covers a
specific sound.**

## B2. Source-by-source

**freesound.org** — the largest and most specific-search-friendly library.
Individual sounds are licensed **CC0, CC-BY, or CC-BY-NC**, sound by sound, chosen by each
uploader; there is no site-wide licence. **CC-BY-NC is not usable for Blocksmith at all** — it
forbids commercial use outright, and even "commercial" is read broadly enough that a monetised
YouTube video of gameplay footage containing a CC-BY-NC sound has been treated as a breach in
community discussion
([Freesound forum](https://freesound.org/forum/legal-help-and-attribution-questions/39864/)).
**Filter to CC0 and CC-BY only when searching**; the site's advanced search supports this but
only one licence family at a time. CC0 needs no attribution; CC-BY needs the standard citation
(B1). Freesound also explicitly discourages scripted bulk-downloading through its API for large
volumes, directing bulk use to its separate **Data Packs Portal** instead
([Freesound API overview](https://freesound.org/docs/api/overview.html)) — relevant to Part D's
tooling choice.

**OpenGameArt.org** — curated specifically for game use, which freesound is not. Accepts only
**CC0, CC-BY 3.0, CC-BY-SA 3.0, OGA-BY 3.0** (a CC-BY variant with the anti-DRM clause removed)
and GPL/LGPL family licences; nothing narrower is allowed on the site at all
([OpenGameArt FAQ](https://opengameart.org/content/faq)). Has several **dedicated CC0 SFX
collections already curated for exactly this kind of retro/blocky game** — "100 CC0 SFX"
and its sequel, "CC0 Sounds Library," and "Different steps on wood, stone, leaves, gravel and
mud," the last of which is tagged `minecraft`/`minetest`/`building` by its own uploader
([opengameart.org/content/different-steps-on-wood-stone-leaves-gravel-and-mud](https://opengameart.org/content/different-steps-on-wood-stone-leaves-gravel-and-mud)).
**One trap specific to this site**: preview audio embedded in a listing page is not necessarily
under the same licence as the downloadable file — *"preview images or preview audio clips may
not fall under the same licence as the actual downloadable assets... unless otherwise noted,
should be assumed 'All rights reserved'"* ([OpenGameArt FAQ](https://opengameart.org/content/faq)).
Always resolve the licence from the download page, never from a preview player.

**Kenney (kenney.nl)** — **everything on the site is CC0**, no exceptions, no per-asset check
needed. *"Download this package... CC0 licensed!"* is the standard line on every pack page
([Kenney: Impact Sounds](https://kenney.nl/assets/impact-sounds)). Directly relevant packs:
**Impact Sounds** (130 clips), **Interface Sounds** / **UI Audio** (both ~100 clips, aimed
squarely at menu/button feedback), **RPG Audio** (50 clips, foley-style: coins, latches, metal
pots, blade slices — a reasonable match for crafting/inventory sounds), and **Digital Audio**
(synthesised beeps, a plausible UI-click source that would sit stylistically close to a
procedurally-synthesised alternative, see Part D). Kenney is the single lowest-friction source
in this brief: no licence check per file, no attribution obligation, no ambiguity.

**Sonniss GDC bundles** — professional-grade libraries, released free once a year around GDC,
carrying **the same commercial licence as Sonniss's paid catalogue**: *"royalty-free for any
commercial work, with no fees or paperwork required... usable in games you sell"*, and
explicitly **no attribution required**
([Sonniss GDC bundle licence](https://sonniss.com/gdc-bundle-license/)). Two real constraints:
**(a) individual files cannot be resold or redistributed as standalone SFX files** — embedding a
converted clip inside a compiled ROM/CIA is not "reselling the SFX file," so this does not block
Blocksmith's use case, but it does mean *"here are the raw Sonniss files"* could never ship as a
separate downloadable pack; **(b) each year's bundle is large — reported as 30+ GB** — so it
needs to be treated as a source to search and cherry-pick from, not something to bulk-ingest.
**A newer clause worth flagging even though it does not apply here**: the current licence text
explicitly forbids using the sounds for AI/ML training, which is irrelevant to this project but
is one more sign the licence is actively maintained and worth re-reading at time of use rather
than trusted from this brief alone, since a free annual bundle's terms are a moving target across
years. **[NO SOURCE]** for whether older (pre-2020ish) GDC bundle years carry identical terms to
the current page — treat the current `sonniss.com/gdc-bundle-license` page as authoritative and
re-check it at implementation time rather than relying on this brief's paraphrase.

**BBC Sound Effects archive — not usable for this project, flagged explicitly so it is never
reached for by habit.** It is distributed under the **RemArc licence**, which permits *"personal,
educational or research purposes"* only and explicitly states *"samples can only be used for
research, educational or personal projects, and therefore can't be legally sampled in... anything
that is then sold"* ([Avosound: RemArc licence summary](https://www.avosound.com/en-us/licensing/remarc-license)).
Blocksmith is a distributed, if free, piece of software the project intends to keep releasing
publicly (per its own CIA-on-GitHub-Releases convention) — that is not a personal/research use,
so **every clip in the BBC archive is off the table regardless of how good the sound is.** This
is the one source in this brief that looks free at a glance and is not.

**Pixabay** — sound effects (130,000+ clips) under the site-wide **Pixabay Content Licence**,
free for **commercial and non-commercial use, no attribution required**
([Pixabay Content Licence](https://pixabay.com/service/license-summary/)). The one restriction
relevant here: content **cannot be redistributed "on a Standalone basis"** — i.e. re-uploading
the raw sound file as its own product is forbidden, but *"a combination of... audio files, other
media... is not Standalone use, so long as the combined effect is to make a 'new' creative
work"* ([Pixabay Terms of Service](https://pixabay.com/service/terms/)). A sound effect converted
to DSP-ADPCM and compiled into a game binary is unambiguously not standalone redistribution of
the original file, so this restriction does not block use here.

## B3. What "the attribution obligation would concretely mean" — the actual answer

For every CC-BY (and, per B1's caution, CC-BY-SA-if-unmodified) clip used: one line in a
`CREDITS.md` (or an existing README section) of the form *title — author — source URL —
licence*, committed to the repo alongside the converted asset. **No runtime cost, no in-game
credits screen required by any licence read in this brief, no per-frame or per-build
obligation.** CC0 and Kenney assets need no entry at all, though the roadmap's own wording
("credited in the repository") reads as wanting one anyway for traceability — **[INFERENCE]** a
single `CREDITS.md` covering every sourced clip, CC0 included, costs nothing and settles any
future "which licence was this again" question without re-deriving it.

# Part C — What sounds the game actually needs, from the code

Every category below was checked against the tree, not imagined. Two systems the roadmap's own
wording implies ("animals... ambience") **do not exist in the code yet** and are named as such.

## C1. Block breaking and placing — both systems exist today

`source/scene/interact.h` defines `Interact`, driven by `interactEdit()`
(`interact.h:133-134`). Breaking is not an instant act — since v1.8.1 it is a held-button
*process*: `break_ticks` accumulates against a per-block `break_need` computed by
`breakTicksRequired()`, and `INTERACT_BREAK_STAGES` (`interact.h:91`, value **8**) drives an
8-stage crack overlay, the same stage count `tools/make_crack_atlas.py` draws. **This is a
natural hook for a looping or stage-advancing "chip" sound** rather than one triggered on
completion only — the crack overlay already fires once per stage, so a break-in-progress sound
can key off the same event with no new state.

| 14 | FERN | cross-shape, breakable, drops nothing |

**Sound-worthy count: the 7 carriable, placeable full-cube materials (GRASS..PLANKS) each need a
break sound and a place sound — 14 clips if fully per-material, fewer if grouped by acoustic
class** (e.g. GRASS/DIRT can plausibly share a "soft earth" sound; STONE/SAND could each be
distinct; WOOD/PLANKS share "wood"). **[INFERENCE]** Grouping into **4 acoustic classes — earth
(grass, dirt), stone (stone, sand), wood (wood, planks), foliage (leaves)** — costs one lookup
table and covers the full carriable set with **4 break + 4 place = 8 clips**, against 14 for a
fully separate treatment. The register-table shape the block registry already uses
(`block.h:1-4`: *"one table, one row per block"*) makes either choice a one-column addition, not
a structural change.

## C2. Footsteps — the physics exists, the per-material hook does not

`source/world/physics.h` tracks the player as a `Body` with position and `walk_speed`, but
**nothing in the tree currently queries "what block is the player's foot cell right now"** — no
footstep system exists. Building one needs exactly one new read: the block id at
`floor(body.position) - (0, epsilon, 0)`, which is a heightmap-style lookup the world already
supports elsewhere (chunk_render's own light/collision reads use the same pattern). **The same
4-class grouping from C1 covers footsteps for free** — earth/stone/wood/foliage plus **SNOW and
ICE**, which are walkable full cubes not covered by C1's carriable set, for **6 acoustic classes,
6 footstep clips** (with variation achieved by pitch/volume jitter at playback time rather than
extra clips, an established SFX trick that costs nothing in RAM per Part A4).

## C3. Water entry and exit — the state machine exists, no sound hook yet

`source/world/physics.h:192-284` defines `BodyWet` (`BODY_DRY`, `BODY_SURFACE`,
`BODY_SUBMERGED`) and `bodyWetUpdate()`, called once per frame and already hysteretic
(`PLAYER_WET_HYSTERESIS`, `physics.h:114`, 0.25 blocks) specifically so the boundary does not
flicker. **This hysteresis is good news for a splash sound too**, not just for the physics it
was built for: a naive "am I in water" edge trigger sampled every frame would double-fire right
at the threshold; `bodyWetUpdate()`'s existing hysteresis already prevents that; a splash sound
can be driven off the same `wet` transition (`DRY→SURFACE`/`SURFACE→SUBMERGED` and the reverse)
with **no new debouncing logic required. 2 clips — entry splash, exit splash** — cover it; a
third ("underwater ambience loop" for the SUBMERGED state) is plausible but is closer to
"ambience," which C5 flags as not yet scoped.

## C4. Crafting — exists, small

`source/world/crafting.c:79-100` — **4 recipes** (`RECIPE_DIRT_TO_GRASS`,
`RECIPE_STONE_TO_SAND`, `RECIPE_LEAVES_TO_DIRT`, `RECIPE_WOOD_TO_PLANKS`), each an instantaneous
conversion (`craftMake()`, `crafting.c:110-133`) with no animation or multi-tick process. **1
generic "craft success" clip** covers all four; there is no furnace, no smelting, and no fuel
system anywhere in the tree (`crafting.c`'s own header comment at line 68 explicitly rejects
charcoal/fuel as needing systems that do not exist) — **furnace/smelting sounds are out of scope
for what the code can trigger today**, not merely unimplemented.

## C5. What the roadmap names that the code cannot yet trigger

The v1.8.17 roadmap line names **"animals"** and **"ambience"** alongside the systems above.
Neither has any hook in the tree: there is no mob/entity system at all (confirmed by the
codebase audit: zero mobs spawned or moving, no entity registry), and "ambience" implies a
looping background layer with no defined trigger condition (time of day? biome? both are
plumbed per the sky-and-weather brief, but nothing currently reads them for audio purposes).
**[INFERENCE]** These two are the two line items in the roadmap's own v1.8.17 description that
cannot be scoped from the code today — they depend on systems (mob AI, a running day/night
clock) that other future versions own. Recommend narrowing v1.8.17's actual deliverable to what
Part C1-C4 cover (breaking, placing, footsteps, water, crafting, plus UI per C6) and treating
animal and ambience sound as **that content's own future version**, arriving with the systems
that drive it, rather than stubbing sounds for mobs that cannot spawn yet.

## C6. UI — exists, no distinct sound events yet

`source/scene/ui.h:66-87` tracks raw touch state (`touch_prev` for edge detection) but nothing
currently fires a discrete "button pressed" event distinguishable from "finger moved." **A UI
click sound needs the same edge-detection idiom `interactEdit()` already uses for its own button
presses** (`Interact.prev_keys`, `interact.h:54-56`) applied to the touch path — a small, local
change, not a new pattern. **2-3 clips** (generic tap, a distinct "denied/can't do that" buzz for
refused actions — `interactEdit()` already has a `refused` counter at `interact.h:53` to key off
of) covers it.

## C7. Total count

**[DERIVED]**, summing the above at the grouped (not fully-per-material) granularity:

| Category | Clips |
|---|---|
| Block break (4 acoustic classes) | 4 |
| Block place (4 acoustic classes) | 4 |
| Footsteps (6 classes: earth, stone, wood, foliage, snow, ice) | 6 |
| Water entry/exit | 2 |
| Crafting | 1 |
| UI (tap + denied) | 2-3 |

Add 2-3 pitch/volume variants per clip at playback time (no extra RAM, per A4) for texture, and

enough that Part B's curated CC0 packs (Kenney's Impact/Interface/RPG Audio, OpenGameArt's
Minecraft-tagged footstep packs) plausibly cover the whole list without needing Sonniss's or

# Part D — Sourcing plan and format pipeline

## D1. Sourcing plan, by category

| Category | Primary source | Why | Licence |
|---|---|---|---|
| Footsteps (earth/stone/wood/foliage/snow/ice) | OpenGameArt: *"Different steps on wood, stone, leaves, gravel and mud"* (tagged `minecraft`/`minetest`) and *"Foot walking step sounds on stone, water, snow, wood and dirt"* | Purpose-built for exactly this genre and material list already | CC0 |
| Block break/place (earth/stone/wood/foliage) | Kenney **Impact Sounds** (130 clips) | CC0, no per-file check, large enough to cherry-pick 4-8 distinct hits/thuds | CC0 |
| Water entry/exit | Freesound, filtered to CC0 (e.g. qubodup's splash recordings, already relicensed CC0) | Freesound's breadth is needed here — OpenGameArt/Kenney have few dedicated splash sounds | CC0 (must filter per-clip) |
| Crafting | Kenney **RPG Audio** (coin/latch/metal-pot foley) | Already CC0, already foley-styled, matches "something assembled" | CC0 |
| UI tap / denied | Kenney **UI Audio** / **Interface Sounds**, or **procedural synthesis** (D3) | Either is free; procedural keeps zero external dependency for the cheapest category | CC0, or N/A |
| Gap-filling / anything not covered above | Sonniss GDC bundle (search only, no bulk ingest) | Largest, highest-quality catalogue; no attribution; heavier to search | Sonniss GDC licence, no attribution |

Pixabay and general (non-CC0-filtered) Freesound remain viable fallbacks for any specific gap;
BBC is excluded entirely (B2). Every row above resolves without ever touching a CC-BY-SA source,
which sidesteps B1's ambiguity rather than resolving it — the simpler outcome.

## D2. The conversion pipeline — house style is a `tools/` script

The project's own convention, demonstrated by `tools/make_atlas.py`, `tools/make_font.py`, and
directly by `tools/make_banner_audio.py` (the one existing audio-generating script, see the
framing note at the top of this brief), is: **a Python script under `tools/`, using only the
standard library where practical, produces a build artefact deterministically, and is re-run at
package time by `tools/make_cia.sh`.** `make_banner_audio.py` already proves the exact target
format is trivial to hit with nothing but `wave` and `struct` from the stdlib — it writes 22050
Hz mono 16-bit PCM directly with Python's `wave` module (`make_banner_audio.py:39,192-198`), no
external library at all.

**[INFERENCE] Recommendation: `tools/make_sfx.py` (or one script per category if the source
manifest gets large), following the same shape:**

1. **Input:** a small checked-in manifest (e.g. `tools/sfx_manifest.json`) listing, per clip: the
   source file path (checked into a `raw/` or similar staging area — see D2a on whether raw
   source audio belongs in the repo), the licence, the attribution string, and the target
   acoustic class/event name.
2. **Conversion:** downstream of Python's stdlib `wave`/`audioop` for anything already a WAV, or
   a single `ffmpeg` shell-out for the OGG/MP3/FLAC files real-world CC0 packs are commonly
   distributed as (`ffmpeg -i in.ogg -ar 22050 -ac 1 -f s16le out.raw` is the whole of it) —
   **[INFERENCE]** `ffmpeg` is the pragmatic choice here rather than writing OGG/FLAC decoders
   from scratch in Python; it is a build-time-only dependency (like `bannertool` already is for
   the CIA pipeline), never linked into the 3DS binary, so it does not compromise the "nothing
   borrowed, nothing but the standard library at runtime" ethos the visual asset scripts follow
   — that ethos is about the *shipped binary and its assets*, not about the build machine's
   toolchain, which already depends on `bannertool` and devkitARM.
3. **Target format, PCM16 first, ADPCM as a follow-up optimisation, not a blocker.** Per A4, RAM
   is not the binding constraint for a ~20-clip library, so **[INFERENCE] ship PCM16 mono at
   22050 Hz for v1.8.17's first pass** — it needs no coefficient-table encoder, `ndspChnSetFormat`
   support is a one-line call, and the ~0.7 MiB total (Part A4's 20-clip PCM16 row) is a rounding
   error against either console's headroom. **Revisit DSP-ADPCM only if a later version's clip
   count grows enough to matter** — the encoder path exists and is proven
   (`Thealexbarney/gc-dspadpcm-encode`, A2) but is extra tooling complexity this version's real
   RAM numbers do not justify yet.
4. **Output:** raw PCM files (or a small custom header + raw samples — no need for a `.bcstm`/
   `.bcwav` container parser; NDSP consumes raw sample buffers directly via `ndspChnWaveBufAdd`,
   so a container format would be pure overhead) written into `romfs/sfx/`, a folder that does
   not exist yet and needs creating.
5. **Verification, matching `make_banner_audio.py`'s own pattern exactly**: that script's
   `report()` function (`make_banner_audio.py:201-226`) re-opens the file it just wrote and
   prints what the *file's own header* says — rate, channels, bit depth, first/last sample (must
   be 0 or it clicks), peak level — rather than trusting the constants that generated it. The
   new script should do the same for every converted clip: this is a cheap, real check that
   catches a wrong sample rate or a non-zero-crossing edit point before it ever reaches hardware.

**D2a — where source audio lives, an open question for the owner, not a call this brief makes.**
Visual assets have no equivalent question because they are pure code output with no external
input file. Sourced SFX do have an external input file, and it has to live somewhere between
download and conversion. Two options: (a) commit the original downloaded files into the repo
under something like `tools/sfx_source/`, so the conversion is reproducible and auditable
against the manifest's stated licence at any point in the future; (b) keep only the manifest
(source URL, licence, attribution) checked in, and treat the downloaded originals as a
build-time-only fetch, gitignored like `cia/build/`. **[INFERENCE]** (a) is more defensible if a
licence is ever challenged — the exact file that was used is provable, not just linked — at the
cost of repo size; a ~20-clip library at source quality is unlikely to add more than a few MB.
This is a real decision, not an implementation detail, and belongs to the project owner rather
than being picked here.

## D3. Procedural synthesis as a supplement, not a replacement

`tools/make_banner_audio.py` is proof this project can synthesise a musical, textured sound (a
four-note chime with additive harmonics and a noise transient) from nothing but `math` and
`struct`. **[INFERENCE]** That approach is a genuinely good fit for the **UI category
specifically** — clicks, denials, a craft-success chime are exactly the class of short, simple,
tonal-or-noise sounds `make_banner_audio.py` already demonstrates, and synthesising them removes
D1's UI row from the sourcing/licensing question entirely (nothing to attribute, nothing to
licence-check, byte-identical and reviewable like every other procedural asset in the project).
**It is a poor fit for footsteps, breaking, placing and water**, which are inherently
organic/noisy real-world sounds that synthesis can approximate but not really replace without
substantial DSP work the project has no existing code for (impact modelling, granular synthesis)
— those categories should stay sourced per D1. **Recommendation: `tools/make_sfx.py` handles the
sourced categories (D2); a separate, small `tools/make_ui_sfx.py` in the `make_banner_audio.py`
style handles UI clicks/denials procedurally.** This split matches the project's own boundary
between "generated" and "sourced" assets cleanly, rather than blurring it.

# Open questions and gaps

1. **Where sourced SFX originals live in the repo (D2a).** Committing the raw downloaded files
   vs. gitignoring them behind a manifest is a real trade-off between provenance-proof and repo
   size, and it is the owner's call, not this brief's. Consequence of not deciding: the first
   implementation pass will pick one by default and the choice will be harder to reverse once
   `tools/make_sfx.py` and its manifest format exist around it.

2. **DSP-ADPCM vs PCM16 for the shipped format.** Part A4/D2 recommend PCM16 first because the
   RAM numbers do not currently justify ADPCM's extra encoder complexity. If a later version's
   clip count grows past roughly 100-150 clips, or streaming music is added (A4's explicit
   out-of-scope call), that math changes and ADPCM becomes worth its own tooling pass. Revisit
   with real numbers at that point rather than pre-optimising now.

3. **Whether the `dspfirm.cdc`-missing fallback (A3) needs to be visible to the player at all**,
   or should be entirely silent. This brief recommends silent (matching current, audio-less
   behaviour exactly) as the cheapest correct answer, but a one-line "Sound unavailable — see
   [help link]" message in a settings screen is a legitimate alternative the owner may prefer.
   **[NO SOURCE]** for how other CIA homebrew titles typically handle this — not researched, out
   of this brief's scope, worth a quick look if the silent option feels wrong in playtest.

4. **The exact acoustic-class groupings in Part C (4 break/place classes, 6 footstep classes)**
   are this brief's own inference from the block registry, not a rule the code enforces anywhere.
   A different grouping (fully per-material, or coarser than proposed) is a cheap change to the
   lookup table Part C recommends and does not affect anything else in this brief — flagged so
   it is picked deliberately rather than by whatever the first implementation happens to reach
   for.

5. **Animal and ambience sound (C5)** are named in the roadmap's own v1.8.17 line but have no
   hook in the code today, because mob AI and a running world clock (per the sky-and-weather
   brief) do not exist yet either. Recommend descoping them from v1.8.17's actual deliverable;
   this is a scope call for the owner, not a decision this brief makes unilaterally.

6. **Whether official NDSP streaming/example code currently builds and produces sound at all**
   on this project's toolchain version (A2) is genuinely unverified — the cited GitHub issue is
   real but its toolchain-version scope was not narrowed further. The very first implementation
   step should be a from-scratch five-second test tone on real hardware, before any game-event
   wiring, specifically to settle this before it costs debugging time later.

7. **Beta 1.7.3's own sound effects are not sourced anywhere in this brief and were not
   researched** — Minecraft's audio is explicitly off-limits per the hard constraint stated at
   the top, so unlike the sky-and-weather brief there is no "what did the reference version
   actually sound like" research to reconcile against. Every sound in Part C is scoped from
   Blocksmith's own mechanics, not from any Minecraft-era behaviour.
