## Part A — Research: how Minecraft actually carries biome tint

### A1. The colormap: a grayscale texture times a 256x256 PNG

Minecraft does not paint grass green in its texture files. `grass_block_top.png` is a
mostly-neutral, low-saturation noise texture; the actual hue comes from multiplying it,
per pixel, by a colour sampled from `assets/minecraft/textures/colormap/grass.png` — a
**256x256 image**, indexed by the biome's **temperature** (X axis) and **downfall** (Y
axis), both clamped to 0..1 and the downfall further multiplied by temperature so the
usable region is a lower-left triangle of the square, not the whole square. A hot, wet
biome (jungle) reads from the far corner; a cold biome (snowy plains) reads near
temperature 0. The same two colormaps (`grass.png`, `foliage.png`) and a third
(`dry_foliage.png`) drive grass, most tree leaves, vines, sugar cane, and — with
different formulas — water and sky colour too.
[Grass Block – Minecraft Wiki](https://minecraft.wiki/w/Grass_Block);
[Minecraft Biome Tint Explained](https://resourcepackcreator.com/biome-tint);
[Colormaps – OptiFine docs](https://optifine.readthedocs.io/colormaps.html).

**One worked example, so the shape of the numbers is concrete:** a grass block at
temperature 0.5, downfall 1.0 resolves to `#7cbd6b`. [Grass Block – Minecraft
Wiki](https://minecraft.wiki/w/Grass_Block). Warm biomes (Badlands, temperature 2.0 —
Minecraft's temperature scale runs past 1.0, unlike Blocksmith's 0..1 fixed-point field,
see B5) skew yellow-brown; cold biomes (Snowy Plains, 0.0) skew blue-green.

**A named exception worth knowing about, because Blocksmith's own biome table has an
analogous "special case" shape.** Swamp does not read the colormap grid at all — its
grass colour is chosen by a separate 2D noise test (`< -0.1` picks one fixed colour,
otherwise another), independent of temperature/downfall. [Grass Block – Minecraft
Wiki](https://minecraft.wiki/w/Grass_Block). The lesson for Blocksmith is not "copy the
swamp rule" (there is no swamp — `worldgen.h:281-287` explicitly rejected that name for a
measured art reason) but that **the colormap-grid model does not have to be the only
rule**; a biome whose tint genuinely needs an out-of-grid special case is allowed one.

### A2. Which faces actually get tinted — the overlay technique

The grass block's **top** face uses one texture and tints the whole thing. The **sides**
do not: Java Edition ships two separate side textures, `grass_block_side.png` (the plain
dirt-brown base, never tinted) and `grass_block_side_overlay.png` (a mostly-transparent
strip showing only the green fringe, which **is** tinted and is alpha-blended over the
base). The block model's JSON marks the top face and the four overlay faces with
`"tintindex": 0`; the base side faces carry no tint index at all. [How do grass block
textures work? – Planet Minecraft
forum](https://www.planetminecraft.com/forums/communities/texturing/how-do-grass-block-textures-work-594118/);
corroborated independently by a second forum thread describing the same
base+overlay+tint layering explicitly.
[Grass Blocks and In-Game Tint? – Minecraft
Forum](https://www.minecraftforum.net/forums/mapping-and-modding-java-edition/resource-packs/resource-pack-help/2985911-grass-blocks-and-in-game-tint).
Bedrock Edition, notably, does **not** keep the two side layers separate — it pre-merges
them into one texture file at content-build time. [same source].

This is a two-texture-sample, alpha-blend-per-fragment technique. It needs a fragment
stage that can sample two textures and blend by the second one's alpha — which costs a
second texture unit and at least two more TexEnv stages on a PICA200 (Part C4 works the
budget). **This is exactly the class of feature the "no programmable fragment shader"
constraint should make Blocksmith decline**, and Part C4 recommends declining it — the
side face is already the block steve explicitly praised, unchanged.

### A3. Biome borders: a real-time blend, not a baked colormap gradient

Vanilla's grass/foliage/water colour at a border between two biomes is not read as one
colormap sample — it is the **average of several nearby biomes' colours**, recomputed
by the renderer. The client's "Biome Blend" video option controls the sample window: a
square from **3x3 up to 15x15 blocks**, and *"larger settings exponentially increasing
the number of points that must be blended for every block that uses it, affecting chunk
update time rather than steady-state FPS."* [What does biome blend do exactly? –
Minecraft
Forum](https://www.minecraftforum.net/forums/minecraft-java-edition/discussion/2914678-what-does-biome-blend-do-exactly);
[Minecraft: Here's What Biome Blend Setting
Is](https://fictionhorizon.com/what-does-biome-blend-do-in-minecraft/).

**This blend is baked into the chunk mesh at build time, the same way Blocksmith already
bakes AO and light into `MeshVertex`.** [INFERENCE, from the community sources above —
not independently confirmed against Mojang source] The averaging is what "chunk update
time, not steady-state FPS" means: it costs something when a chunk (re)meshes, and
nothing per frame afterwards, which is precisely the shape Blocksmith's own light/AO
baking already follows (`world/mesher.c` bakes `cornerLight()` into `MeshVertex.pad`
once per remesh — cited in `docs/research/sky-and-weather.md` D2). This is good news:
whatever tint-blending Blocksmith adds does not need a new *kind* of cost, it needs to
reuse a cost the project already pays.

**A technical critique of the grid approach, cited because it names the actual visual
failure mode a grid-based blend produces**, and because Blocksmith's own biome field is
already continuous (B5) and can sidestep it: *"generators skirt around performance
problems by generating everything on a lower resolution grid, then interpolating between
the gaps — this prevents borders from producing angular variety below the grid's scale,
pulling borders into alignment with grid edges... and creates regularly-spaced creases."*
[Fast Biome Blending, Without Squareness –
noiseposti.ng](https://noiseposti.ng/posts/2021-03-13-Fast-Biome-Blending-Without-Squareness.html).
Minecraft is named in that piece as the example of the grid problem. Part C2 proposes a
design that reads Blocksmith's continuous temperature/humidity fields directly per
vertex rather than blending a discretised biome id, which sidesteps this failure mode by
construction rather than by a bigger blend radius.

## Part B — Read-only survey of Blocksmith's own code

All line numbers read from the tree on 2026-09-01. Nothing in `source/` or `tools/` was

### B1. The block id space — and a correction to how the task brief frames it

The task brief for this version says "BLOCK_COUNT must be lifted in lockstep with the
server." That is **true for exactly one reason and false for the reason it sounds like**.
Read carefully:

- `world/block.h:29`: `BLOCK_COUNT` closes the enum at **8** (`AIR GRASS DIRT STONE SAND
  WOOD LEAVES PLANKS`), and `block.h:121` static-asserts it stays there.
  `deps/blocksmith-server/game/validate.c:146` static-asserts
  `BLOCK_COUNT == BS_BLOCK_COUNT` — so yes, if this number ever moves, the server's
  vendored copy has to move with it, in the same commit, or the build fails. **But**
  `block.h:40-59` states directly what this number actually bounds: *"BLOCK_COUNT has
  exactly one live use left in this client — `inventoryCanHold()`... the ceiling on what
  a slot may carry."* It is the **item-carry ceiling**, not the ceiling on how many kinds
  of block can exist in the world.
- The actual world-block-id space is `world/registry.h:27-30`: `REG_ID_CORE_LO = 0x01`
  through `REG_ID_CORE_HI = 0x7F` — **127 compiled-in core ids**, of which 15 are used
  today (`BLOCK_AIR`..`BLOCK_FERN`, ids 0..14, `block.h:17-120`). A block that is drawn,
  breakable, and walkable but never picked up — exactly what water, tall grass, snow,
  ice, cactus, dead bush and fern already are, per `block.h:32-129`'s own long comment —
  costs a `registryRegister()` row in this 0x01..0x7F space and **does not touch
  `BLOCK_COUNT` at all.**

**What this means concretely for v1.8.8's block list:** per-biome wood, leaves, planks,
dirt-cap variants, short/tall/2-tall grass, biome-specific flowers, and a redone dead
bush can **all** be added as ordinary non-item core rows in the free space between id 15
and id 127 (112 ids of headroom [DERIVED, 127 − 15]) with **zero server changes**,
exactly the pattern `block.h:61-109` already used for snow/ice/cactus/dead_bush/fern.
**The one thing that genuinely forces a `BLOCK_COUNT` move — and therefore a
client/server lockstep change, per `validate.c:146`'s static assert and
`deps/blocksmith-server/game/validate.h:43-66`'s comment on why the two must never drift
— is a block that must be *carryable*.** Nothing in the owner's stated requirements for
this version asks for that (`docs/ROADMAP.md:257`'s apple item is the one thing in the
roadmap text that would need it, and apples are not in the requirements list this brief
was asked to serve — flagged, not solved, here).

**So: the task brief's instruction to "research/record what needs lockstep" has a real,
useful, narrower answer than "everything does."** Cosmetic and scenery blocks: no
lockstep. A carryable item: yes, lockstep, exactly as the brief warns.

### B2. Durability — the existing toolless hardness scale, and what to extend it with

`world/registry.c:17-38` documents the whole scale in one place: hardness is in **ticks
at 20 TPS**, tuned for a toolless game (no tools exist yet — `registry.c:26-29`), and the
shipped numbers are:

| Class | Ticks | Seconds | Rows today |
|---|---|---|---|
| Plant matter (CROSS shape) | 1 | 0.05 s | tall grass, dead bush, fern |
| Leaves | 4 | 0.20 s | leaves |
| Loose ground (sand) | 10 | 0.50 s | sand |
| Loose ground / ice | 8–10 | 0.40–0.50 s | snow (8), ice (10), cactus (8) |
| Packed ground (grass, dirt) | 12 | 0.60 s | grass, dirt |
| Timber | 40 | 2.00 s | wood, planks |
| Mineral | 45 | 2.25 s | stone |

This is a real, tuned, internally-consistent scale, not a placeholder — `registry.c:204-214`
explicitly re-derives snow/ice/cactus's numbers *against* this same scale ("softer than
sand", "sand's number", "plant matter, not timber") rather than inventing new ones.
**[DERIVED] recommendation: every new biome-identity block should be assigned to one of
these existing classes by material, not given a bespoke number:**

| New block | Class | Ticks | Reasoning |
|---|---|---|---|
| Per-biome log/wood | Timber | 40 | Same material as the existing wood row |
| Per-biome planks | Timber | 40 | Same material as the existing planks row |
| Per-biome leaves | Leaves | 4 | Same material as the existing leaves row |
| Short grass (new shape) | Plant matter | 1 | Same class as tall grass |
| 2-tall grass, both halves | Plant matter | 1 | Same class as tall grass — see D6 |
| Biome-specific flowers | Plant matter | 1 | Same class as fern/dead bush |
| Dead bush, redone | Plant matter | 1 | Unchanged from the shipped row (`registry.c:262-268`) — the redesign is art, not hardness |

The `.hardness` field is a single byte per `BlockDef` (`registry.h`'s packed struct,
27 bytes, `_Static_assert` at `registry.h:96`), so this costs nothing structurally — it
is exactly the same field every existing block already fills in.

**Fixed — cactus cannot currently be broken.** The roadmap text (`ROADMAP.md:261-262`)
names this directly as a bug to fix in this version. `registry.c:250-256` shows cactus
already has `.hardness = 8` and `REG_FLAG_SOLID` with no shape flag override, which reads
as a *complete* row — **the break-refusal is not a hardness problem, it is the same
`BLOCK_COUNT` ceiling B1 explains**: cactus is id 12, past the ceiling of 8, so
`inventoryCanHold()` answers false and `scene/interact.c`'s guard
(`!blockDropsNothing(here) && !inventoryCanHold(here)`) refuses the break outright,
exactly as `block.h:194-199`'s comment states in as many words for snow/ice/cactus as a
class: *"scenery... you can walk on them, aim at them and build against them, and you
cannot mine them."* **This is very likely by design, not a bug** — the same comment
calls it *"the same end state world/block.h argues for water."* If the roadmap entry
means "cactus should actually be minable," that is a `BLOCK_COUNT`-ceiling change (B1)
or a `blockDropsNothing()`-style predicate widening, either of which is the owner's call,
not an assumption this brief should make. **Flagged for the owner, not resolved here.**

### B3. The vertex format — the load-bearing constraint

`world/mesh_vertex.h:11-27`, `MeshVertex`, locked at exactly 8 bytes
(`_Static_assert(sizeof(MeshVertex) == 8, ...)`, line 68):

```c
typedef struct {
    int8_t  x, y, z;   // position, chunk-local 0..16
    int8_t  pad;       // packed light: sky * 16 + block
    uint8_t u, v;      // atlas coordinates
    uint8_t nrm;       // face index (bits 0-2) + water-drop (bits 3-5)
    uint8_t ao;        // ambient occlusion, 0..3
} MeshVertex;
```

**There is no RGB colour field.** What the TexEnv stage 0 calls "the vertex colour"
(`GPU_PRIMARY_COLOR`, `chunk_render.c:808`) is computed **in the vertex shader**, from
`pad` (light) and `ao`, and it is a single scalar:
`shaders/world_dynamic.v.pica:176-178`:

```
mul r6.y, r3.xxxx, r4.xxxx    ; faceShade x aoCurve
mul r6.z, r6.yyyy, r5.wwww    ; x lum
mov outclr.xyz, r6.zzz        ; broadcast the ONE scalar to R, G and B
```

So today's pipeline has never carried a hue at all — brightness only. This is the fact
the task brief's "the greedy mesher already emits [per-vertex colour]" line gets wrong on
two counts: the mesher is explicitly not greedy (`mesher.h:8-11`, quoted in the headline
above) and the colour it emits is grayscale.

**The good news, and it is real news:** `ao` is declared `uint8_t` but only ever holds
**0..3** (`mesh_vertex.h:26`, `"ambient occlusion 0..3"`) — **6 of its 8 bits are unused
today.** That is enough room to pack a small tint-lookup index alongside AO with zero
growth to the vertex, zero change to the 8-byte stride, and zero risk to the
hard-won alignment invariant `mesh_vertex.h:40-66` fought a real console hang to
establish (`_Static_assert(offsetof(MeshVertex, u) == 4, ...)`, line 64-66). Part C2 uses
this directly.

### B4. TexEnv and texture-unit budget — carried over from `sky-and-weather.md`, re-verified here

`chunk_render.c:806-809` (stage 0, atlas x vertex colour) and `chunk_render.c:882-890`
(stage 1, fog) are the only two of six TexEnv stages in use; stages 2-5 sit at citro3d's
default passthrough. Confirmed independently for this brief at the same line numbers the
sky-and-weather brief cites. Texture units: `atlasBind()` (unit 0) and `fogTexBind()`
(unit 1) are the only two bound; **unit 2 is free.** Both facts corroborated by
[GBATEK's TexEnv register
documentation](http://problemkaputt.de/gbatek-3ds-gpu-internal-registers-texturing-registers-environment.htm)
and citro3d's own source, which confirm **each of the 6 stages carries its own
independent constant-colour register** (`GPUREG_TEXENV0_COLOR` through `TEXENV5_COLOR`,
offset `id*8` apart) rather than sharing one global constant — so a tint stage, if one is
used, is not fighting the fog stage for its constant.
[citro3d `texenv.c`](https://github.com/devkitPro/citro3d/blob/master/source/texenv.c).
A TEV-buffer write in one stage is not readable until **two stages later**
(`docs/research/sky-and-weather.md` D3, re-confirmed by the same GBATEK page).

### B5. The biome field — continuous, uncached, and already the right shape for a colormap

`world/worldgen.h:288-296`: six biomes, a 3x2 grid, `BIOME_TUNDRA`..`BIOME_JUNGLE`,
`BIOME_COUNT = 6`. Both axes are **continuous fixed-point fields in [0, FX_ONE]**
(`worldgenBiome()`, `worldgenHumidity()`), only thresholded into a discrete `BiomeId` at
classification time (`worldgenBiomeAt()`, `worldgen.c:175`). This is exactly Minecraft's
own (temperature, downfall) axis pair (A1) — Blocksmith already has the two continuous
inputs a colormap-style tint needs, per column, without adding any new noise field.

**Not cached.** `docs/research/sky-and-weather.md` D5a already establishes this and it
still holds: every call to `worldgenBiomeAt`/`worldgenBiome`/`worldgenHumidity` runs a
fresh 2-octave `noiseFbm2` per axis. For **mesh-time tint baking** (Part C2's
recommendation) this cost is paid once per chunk remesh, not once per frame, which is an
acceptable place to pay it — the same place light and AO already pay their cost. For the
**bottom-screen "current biome" debug readout** (Part E2) it would be paid every frame
the debug menu is open unless the caller reuses a value already computed for something
else nearby; flagged as a real but small cost, not a blocker.

### B6. Debug menu — a text-row registry, no icon support

`app/debugmenu.h:19-48`: four entry kinds — `DEBUG_TOGGLE`, `DEBUG_SLIDER_INT`,
`DEBUG_ACTION`, `DEBUG_INFO` — each a name string plus a getter/setter/callback, in a
fixed pool of `DEBUG_MENU_MAX_ENTRIES = 32` (line 17). There is **no icon, image, or
grid-layout concept anywhere in this file.** A toggle (neon borders) and an info row
(current biome) fit this registry exactly as it exists — `main.c:1119-1174`
(`bsDebugRegister`) already shows the pattern for both kinds. **A block list with icons
does not fit this registry at all** — it needs its own screen, opened by a `DEBUG_ACTION`
row the same way `debugMenuUiOpen()` already opens the debug menu itself
(`main.c:4285-4287`), not a 33rd entry in the list.

### B7. Existing icon-drawing precedent for the block list

`scene/ui.c:184`: `const AtlasRect r = atlasTile(blockFaceTex(id, FACE_TOP));` — this is
the exact call the hotbar/inventory grid already uses to turn a `BlockId` into an atlas
rect for a slot icon, and the surrounding comment (`ui.c:160-184`) confirms the
coordinate-space handling (pixel columns vs. slot-edge rows) is already solved there.
`registry.c:260-261`'s comment on the CROSS blocks — *"All six tex entries carry the same
tile because mesher.c's emitCross takes FACE_EAST's rect for the whole shape"* — means
`FACE_TOP` resolves correctly for a plant icon too, with no special-casing: a flower's
icon is just its one shared texture, the same call as a cube block's top face. **The
block list's icon rendering is a direct reuse of this call, once per registered block id,
laid out as a grid instead of a hotbar strip.**

### B8. Existing outline-geometry precedent for the neon border toggle

`scene/highlight.c:1-46`: the block-cursor cage is **twelve thin axis-aligned boxes**
(`HL_BOXES = 12`, `HL_TRIS_PER_BOX = 12`, 432 vertices, no index buffer), drawn with its
**own tiny shader and its own vertex format** — plain `{float x, y, z}`, no texture, no
lighting, **colour supplied by a TEV constant, not a vertex attribute**
(`highlight.c:16-18`). This is a complete, working, already-shipped example of exactly
the mechanism a neon-biome-border overlay needs: a debug-only outline drawn in a second,
cheap pass, coloured by a TexEnv constant that can be swapped for a neon value with zero
change to the world mesh or its shader. Part E1 gives the concrete adaptation.

### B9. Atlas tooling — procedural, and not yet tint-ready

`tools/make_atlas.py:1-6` states the project's own no-copying rule in its own words:
*"nothing is traced, sampled or copied from another game... the palette is deliberately
its own."* Every tile is a Python function taking an RNG and returning pixels
(`tile_grass_top`, `tile_dirt`, `tile_wood_side`, etc., `make_atlas.py:201-356`) built
from a small `speckle()` helper that blends weighted colour lists per pixel
(`make_atlas.py:187-199`).

**`tile_grass_top` is fully saturated green today**
(`make_atlas.py:201-210`: base colours `(58,112,74)`, `(66,126,82)`, `(74,138,90)`,
`(50,100,66)`, with brighter-blade highlights at `(88,152,100)`) — **not** the
mostly-neutral, low-saturation base Minecraft's own `grass_block_top.png` is (A1). **If a
per-biome tint is multiplied onto this texture as it stands, the result compounds two
saturated greens rather than letting the tint carry the hue**, which is the same failure
mode a resource-pack author hits when they forget to desaturate a custom grass texture
before relying on tint (a documented, recurring complaint in the Minecraft resource-pack
community, cross-referenced across three of the forum threads found for A2). **[INFERENCE]
This is a concrete, required change to `tools/make_atlas.py`, not an optional one: the
grass-top tile (and any CROSS-shape tile meant to carry biome tint — tall grass, short
grass, ferns) needs a desaturated/near-neutral variant generated alongside or in place of
the current one, so `GPU_MODULATE` has room to do the actual colouring.** This is a
Python change, entirely within the project's existing procedural pipeline — no new asset,
no copied palette, exactly the practice `make_atlas.py`'s own header commits to.

### B10. Existing per-biome scatter precedent — the model for adding flowers and grass variants

`world/worldgen.h:326-393` already runs a **one-shape-many-biomes** pattern: `BLOCK_FERN`
is a single block id, and only its **chance of appearing** varies by biome
(`GEN_FERN_TAIGA = 20`, `GEN_FERN_JUNGLE = 32`, both resolving to the same `BLOCK_FERN`
placement at `worldgen.c:751-764`). Tall grass follows the identical shape:
`GEN_GRASS_TUNDRA..GEN_GRASS_JUNGLE` is one per-biome density table
(`worldgen.h:333-338`) feeding one block id, `BLOCK_TALL_GRASS`. **This is precedent
already shipped in this codebase for exactly the model Part D4 recommends for grass
height variants: one shape, tinted by biome at render time, gated by a per-biome density
table at generation time — never one block id per (biome x shape) combination.**

## Part C — The verdict: carrying biome tint on a PICA200 with no fragment shader

### C1. Two viable designs, and their real costs

**Design 1 — a small tint table in vertex-shader uniform registers, indexed by spare
`ao` bits.** `shaders/world_dynamic.v.pica:103-104` already proves the exact mechanism
needed: `mova a0.x, inpack.zzzz` / `mov r3, faceShade[a0.x]` is **dynamic indexing into a
uniform array from a packed vertex byte**, already shipping, already tested on hardware
(the `faceShade[64]` table). A `tintLUT[N]` array of the same shape, indexed the same way
from the spare bits of `ao` (B3), needs no new vertex attribute, no new texture unit, and
no new TexEnv stage — it is one more `mova`/lookup and one more `mul` in a shader that
already does this exact pattern once.

**Budget, [COMPUTED] from cited numbers:** the PICA200 vertex shader has **96 float
uniform registers** (`c0..c95`, confirmed by devkitPro's picasso shader-assembler manual —
[picasso Manual.md](https://github.com/devkitPro/picasso/blob/master/Manual.md) — and
matching the "96... already spends 77" figure `world/mesher.h:127-129` states
independently for this project's own shader). **77 are already spent** (`mesher.h:129`),
leaving **19 free** [DERIVED, 96 − 77]. At one `fvec4` register per tint entry (RGB in
`.xyz`, `.w` unused or reused for a second purpose later), that is **room for up to 19
tint entries with zero pressure on anything else already using those registers** — enough
for, say, a 4x4 temperature x humidity grid (16 entries) with 3 to spare, but **not**
enough for anything approaching Minecraft's own 256x256 colormap, or even a modest 8x8
grid (64 entries — over 3x the free budget).

**Design 2 — a small colormap texture on the free texture unit, read through a new TexEnv
stage.** Trades register pressure for state and instruction cost: needs one more UV
attribute or a computed UV, a texture bind, and (per B4) at least one more TexEnv stage
(two if the neutral-for-non-tinted-blocks trick in C2 is done via a stage gate rather than
a baked LUT entry). Buys a much larger palette — an 8x8 or even 16x16 lookup texture costs
almost nothing in VRAM (a 16x16 RGBA5551 tile is 512 bytes) — at the cost of consuming one
of the four remaining free TexEnv stages and the two-texture-unit headroom `sky-and-weather.md`
D3 already earmarked as "free" for other v1.8.9 work (rain billboards). **Using it here
competes with that.**

**[INFERENCE] Recommendation: Design 1.** A 4x4 (or even a flat 6- or 8-entry, one per
biome plus a couple of blend steps) uniform-register LUT is well inside the 19-register
free budget, needs no new TexEnv stage (leaving all four free stages for v1.8.9's weather
and any future work), no new texture unit, and reuses an indexing idiom this exact shader
already proves works on hardware. It is the cheaper design in every resource this project
tracks, and it does not foreclose Design 2 later if a genuinely large palette is ever
wanted — the two are not mutually exclusive, and nothing about shipping Design 1 first
makes Design 2 harder to add afterwards.

### C2. Concrete bit-packing and border-blend plan

1. **Reserve 4 bits of `MeshVertex.ao`** (of the 6 spare, B3) for a tint index, `0..15`,
   giving Design 1's 4x4-grid headroom exactly (16 entries, matching the 19-register
   budget with 3 to spare for a future neutral/error entry or a second axis step). The AO
   value itself keeps its existing low 2 bits, unchanged — `ao = (ao_value & 0x3) |
   (tint_index << 2)`, decoded in the shader with a mask before `faceShade`/`aoCurve`
   lookups, exactly the same masking pattern `meshNrmFace()`/`meshNrmDrop()`
   (`mesher.h:108-109`) already use to split the `nrm` byte.
2. **Bake the index at mesh time, not render time**, matching how AO and light are
   already baked (B3) and how vanilla's own biome blend is baked at chunk-build time
   (A3). At the point the mesher currently reads `worldgenBiomeAt`/temperature/humidity
   for a column (already computed during generation — B5), quantise `(temperature,
   humidity)` to the nearest of the 16 grid cells and write that index into every
   tintable vertex's `ao` byte for that column.
3. **This sidesteps the "biome border" problem by construction, not by blending
   afterwards.** Because Blocksmith's temperature/humidity fields are continuous per
   *block*, not per discrete biome region (B5), sampling them at each vertex's own
   position rather than at its owning `BiomeId`'s fixed value already produces a smooth
   gradient across a border — there is no separate "average N neighbours" pass to write,
   because the two inputs were never discretised into a hard region in the first place.
   This is the same reasoning `worldgen_density.h`'s own comment gives for keeping biome
   a label painted onto height rather than a driver of it (cited in
   `terrain-beta-1.7.3.md` C1-adjacent code): **thresholding early is what creates a
   visible seam; reading the continuous field late avoids inventing one.** [INFERENCE —
   this is this brief's own reasoning applied to a different field than the terrain
   brief's, not a re-statement of a measured result]
4. **A neutral entry (RGB `1,1,1`) at index 0** for every block that is not tinted
   (stone, sand, planks, wood sides, dirt, etc.) — the mesher writes index 0 there and
   the `mul outclr.xyz, r6.zzzz, tintLUT[idx].xyz` becomes a no-op multiply by white for
   every non-biome block. This is exactly the same "always-on, harmless where it does not
   apply" shape stage 0's AO multiply already uses for blocks that never occlude.

### C3. Grass strands get the same LUT, for free

Tall grass, short grass and any 2-tall grass halves (D6) are `BLOCK_SHAPE_CROSS`
geometry, meshed by `emitCross` and carrying the same 8-byte `MeshVertex` as every cube
face (`mesher.h:23`, `MeshOut.verts` is one array for every shape). **The tint mechanism
in C2 does not need a special case for plants** — a CROSS vertex's `ao` byte gets the
same packed index, from the same per-column (temperature, humidity) sample, as the grass
block underneath it. This is the direct, mechanical answer to the owner's "grass strands
must be recoloured to match the grass block": **they are driven by the identical LUT
lookup as the block they stand on, so they match by construction, not by a second tuning
pass that has to be kept in sync by hand.**

### C4. Grass block sides: keep them exactly as they are

Per A2, the overlay technique needs a second texture sample and alpha blend — a real,
nonzero TexEnv-stage and texture-unit cost (B4/C1). **[INFERENCE] Recommendation:
decline it.** `tile_grass_side` (`make_atlas.py:226-237`) already renders the grass-fading-
to-dirt look as one flat texture, and this is precisely the block the owner explicitly
praised and asked to keep — *"the half-grass/half-dirt block... he wants it KEPT."*
Leaving the side face **untinted and untouched** is not a compromise forced by hardware
limits, it is the design that costs nothing and changes nothing about the block the owner
already likes. Only the **top** face (`BTEX_GRASS_TOP`) and CROSS-shape plant geometry
need the tint index; every cube's side and bottom faces keep index 0 (neutral) exactly
like stone or sand.

### C5. What this actually requires, end to end

1. `tools/make_atlas.py`: desaturate `tile_grass_top` (and any new grass-strand/flower
   tiles meant to carry tint) toward a neutral base — B9.
2. `world/mesh_vertex.h`: document the repurposed `ao` bits (no size or layout change —
   `sizeof(MeshVertex)` stays 8, the alignment invariant at line 64-66 is untouched
   because nothing moves, only spare bits inside an existing byte gain meaning).
3. `shaders/world_dynamic.v.pica`: one new `.fvec tintLUT[16]` uniform, one mask+shift to
   pull the index out of `inpack`'s ao component, one `mova`/lookup (mirrors the existing
   `faceShade` pattern at line 103-104), one `mul` before the existing
   `mov outclr.xyz, r6.zzz` becomes `mul outclr.xyz, r6.zzzz, tintLUT[a0.y].xyz` (or
   equivalent — the exact register allocation is an implementation detail for whoever
   writes the `.pica`, not a design decision this brief needs to make).
4. `world/mesher.c`: at column-fill time, quantise `(worldgenBiome, worldgenHumidity)` to
   a 4x4 grid index and pack it into the `ao` byte for every tintable vertex.
5. A small Python (or C, host-testable per this project's own convention —
   `world/noise.h`'s stated reason for `<3ds.h>`-free code) generator that produces the
   16 `tintLUT` RGB values procedurally from the same six-biome table already in
   `worldgen.h`, so the palette is generated, not hand-picked pixel by pixel — matching
   `tools/make_atlas.py`'s own practice for every other colour in this game.

None of this touches `BLOCK_COUNT`, the registry wire format, or the server. It is
entirely a rendering-and-generation-side change.

## Part D — Content: blocks, durability, flowers, dead bush, and the grass-variant question

### D1. Real per-biome blocks vs. tint — where the line actually falls

The roadmap text states the rule cleanly (`ROADMAP.md:239-247`): tint for anything that
is the *same material* looking different (dirt caps, grass), **real distinct block ids**
for anything that is *actually a different material* — wood, leaves, planks. This matches
B1's registry-cost finding exactly: a real per-biome wood/leaves/planks row costs one core
registry id each (112 free, B1) and, per B2, slots into an existing durability class with
no new number to invent. **[INFERENCE] Recommendation: this split is already correct as
stated in the roadmap and this brief found nothing in the code that argues against it —
implement it as written.**

### D2. Durability table for the new content

Restating B2's table against the actual new blocks this version adds:

| New block | Class | Ticks |
|---|---|---|
| Taiga / jungle / forest / tundra log (if per-biome logs are added) | Timber | 40 |
| Matching planks | Timber | 40 |
| Matching leaves | Leaves | 4 |
| Short grass | Plant matter | 1 |
| 2-tall grass (both halves) | Plant matter | 1 |
| Biome-specific flowers (each) | Plant matter | 1 |
| Dead bush, redone | Plant matter | 1 (unchanged, `registry.c:262-268`) |

`registry.c:206-209`'s own stated rule — *"every row carries a real number anyway... a
value that is never read should say it is a decision"* — applies identically here: even
if a flower is later made unbreakable by design, write the tick value and say so, do not
leave the field at its zero-fill default.

### D3. Flowers — biome-specific, using the existing scatter idiom

B10 already shows the exact mechanism: a new `GEN_FLOWER_*` chance-out-of-256 table, one
constant per biome, feeding a *shared* `BLOCK_FLOWER_*` id or several distinct flower ids
gated by which biome placed them, following `worldgenFlora`'s existing structure
(`worldgen.c:689-780`) almost verbatim — same salt-per-pass rule, same "draw first, reject
cheap, resolve biome only on a live draw" ordering the file's own comments insist on
(`worldgen.c:714-723`). **[INFERENCE] This is a small, mechanical addition given the
existing pattern — no new architecture, just one more table and one more switch arm.**

### D4. The owner's open question: is grass variety a good idea?

**Yes — as shape variants tinted by the mechanism in Part C, not as a new block id per
(biome x height) combination.** The reasoning, grounded in what is already shipped:

- B10 shows the codebase already has a working, tested pattern for "one shape, many
  biomes, density varies, block id does not": `BLOCK_FERN` is a single id used in both
  taiga and jungle today. Extending grass to short/tall/2-tall follows the identical
  shape — a handful of new shape ids (short grass, the existing tall grass, a paired
  2-tall grass — D6), each usable in every biome that wants it, tinted per C2/C3 rather
  than duplicated per biome.
- The alternative — a distinct block id for "plains short grass" vs. "forest short
  grass" vs. "jungle short grass" etc. — is the combinatorial explosion the roadmap's own
  headline sentence explicitly warns against: *"there is no separate block for desert
  dirt or swamp grass... it costs nothing per biome, where a block per biome costs an ID,
  atlas space, and a lockstep change on the server every time"* (`ROADMAP.md:239-243`).
  Doing that for grass specifically, after just having argued against it for dirt, would
  be the same mistake in a different place. Six biomes x three heights would be 18 ids
  for what C2/C3 already buys as 3 ids plus a shared tint table.
- **Real cost of doing it, quantified as far as this brief can:** 2-tall grass roughly
  doubles the CROSS-geometry vertex count wherever it is placed (two stacked quads-pairs
  instead of one), but only in the biomes whose density table places it, and flora is
  already a small fraction of a chunk's total geometry (`worldgen.h:209-231`'s own
  measurement of the single-height predecessor put a dense meadow at "9.4% of eligible
  ground"). **[NO SOURCE]** for an exact vertex-count or remesh-time delta from adding a
  second grass height — this would need to be measured once the shape lands, the same way
  every other density constant in `worldgen.h` was (B10's cited GEN_GRASS_CHANCE comment
  is itself an example of exactly this kind of measurement having been done before).

So: yes to variety, with the specific shape "more heights and biome-specific flowers,
tint-driven colour, shared block ids" — which is what the owner's own requirement list
and the roadmap text both already point at, and which this brief found direct precedent
for in code that already ships.

### D5. Dead bush, redone

The existing row (`registry.c:262-268`) is a complete, working `BLOCK_SHAPE_CROSS` block
at hardness 1, desert-only per `worldgen.c:735-748`'s existing chance table
(`GEN_DEAD_BUSH_CHANCE = 8`). "Redone" reads as an **art-only** change — a new
`tile_dead_bush` generated by `tools/make_atlas.py` (the function already exists at
`make_atlas.py:669`, so this is a rewrite of an existing generator function, not a new
one) — with no change to shape, placement chance, or hardness required by anything found
in this brief. **[INFERENCE]** If "redone" is meant to include a taller or two-part dead
bush, that would follow D6's paired-CROSS pattern exactly; nothing in the owner's stated
requirements asks for that, so this brief does not assume it.

### D6. Two-block-tall grass, without a new `BLOCK_SHAPE`

`world/block.h:186-190` currently defines exactly two shapes, `BLOCK_SHAPE_FULL_CUBE` and
`BLOCK_SHAPE_CROSS`, with **three bits reserved** in `BlockDef.flags` for future shapes
(`block.h:183-185`: *"slabs and stairs have room without another format change"*).
**[INFERENCE] A 2-tall grass plant does not need a third shape at all** — it can be two
ordinary `BLOCK_SHAPE_CROSS` blocks, an upper half and a lower half, placed as a pair by
the generator and linked only in break behaviour (breaking either removes both), the same
two-block-linked-state idea Minecraft itself uses for its own double plants
([Grass Block – Minecraft Wiki context confirms tall/double plants are two block
states](https://minecraft.wiki/w/Grass_Block) — cited for the shape of the mechanic, not
its code). This means **zero mesher changes, zero new shape-bit consumption**, only:
a second block id (core space, B1), a break-both rule in `scene/interact.c` (the file
`block.h:244-257`'s comment already identifies as the one that owns this class of
decision), and a generation-time check that the cell above is also clear before placing
the pair — a smaller version of the same `cellsClear()` helper `worldgenFlora` already
uses for cactus height (`worldgen.c:662-670`).

## Part E — The three debug requirements

### E1. Neon biome-border toggle — debug only, never a game feature

**Mechanism:** reuse `scene/highlight.c`'s box-append helper (B8) rather than building a
new renderer. Instead of one 12-box cage per targeted block, draw **one tall thin box per
boundary column** — from `y=0` to `y=WORLD_HEIGHT` (128, per `terrain-beta-1.7.3.md` B2),
at every `(x,z)` where `worldgenBiomeAt(x,z)` differs from its `+x` or `+z` neighbour.
This is a direct call to the same `appendBox`-shaped helper `highlight.c` already has,
just with world-height bounds instead of unit-block bounds, and a **debug-toggle-driven
TEV constant colour** instead of the cursor's fixed one — `highlight.c:16-18` already
states colour comes from a TEV constant, not a vertex attribute, so swapping in a neon
value costs one uniform write, not a shader change.

**Cost, [INFERENCE] not measured:** one box (36 vertices, the same box-append cost
`highlight.c` already pays per edge) per boundary *column*, not per boundary *block* —
a column-tall beam is 128x fewer boxes than one per block, at the cost of not showing
exactly where along the height a biome boundary would be (which is moot, since B5
confirms biome is a 2D field with no height component — a boundary column's beam is
correct at every height by construction, not an approximation). **Only regenerate the
boundary list when a chunk column's biome-adjacent neighbours actually change** — which,
since biome is a pure function of world `(x, z)` (B5) and does not change once generated,
means the boundary list for a loaded radius can be built once when chunks load and never
touched again until the render radius changes. This should be measured against a real
render-distance's worth of boundary columns before shipping — flagged, not measured, here.

### E2. Current biome on the bottom-screen debug readout

**Mechanism:** a `DEBUG_INFO` entry (B6), reading `worldgenBiomeAt(g, player_x, player_z)`
and formatting the biome's name string. `worldgenBiomeParams()`
(`worldgen.h:530`) already returns a `const BiomeParams*` "never NULL" for any id, so the
lookup path is safe by construction; a small name table alongside it (or a name field
added to `BiomeParams` itself) is the only new code.

**Cost:** B5's "not cached" finding applies directly — this is one more uncached
`worldgenBiomeAt` call per frame the debug menu is open, i.e. two `noiseFbm2` evaluations
per frame (temperature + humidity axis). This is the same open gap
`docs/research/sky-and-weather.md`'s Open Question #2 already flags for a different
caller of the same function; it is cheap enough for a once-per-frame debug read (unlike
the per-block scatter cost that function's other callers pay), but it is not free, and it
is one more reason a per-column temperature/humidity cache (already recommended
independently by the sky-and-weather brief for its own purposes) would pay for itself
twice over if it is ever built.

### E3. Block list, icons and names, bottom screen

**Mechanism:** this cannot be a `DebugEntry` row (B6 — the registry has no icon or grid
concept). It needs its own screen, opened by a `DEBUG_ACTION` entry the same way the
existing debug menu itself is opened (`main.c:4285-4287`), drawn on the bottom screen the
same way the inventory/hotbar panel already is (`main.c:2299-2347`,
`#if BS_BOTTOM_UI` guarded, matching every other bottom-screen panel in this build).

**Icon rendering:** direct reuse of `scene/ui.c:184`'s `atlasTile(blockFaceTex(id,
FACE_TOP))` call (B7), laid out as a scrolling grid instead of a hotbar strip — the same
call already correctly handles both cube blocks and CROSS-shape plants (B7's citation of
`registry.c:260-261`), so flowers, grass, and every other new plant block need no
special-casing in the icon path.

**Enumeration:** every registered `BlockId` from `blockInfo()` (`block.h:210`), which
"never returns NULL" for any id — the natural range to walk is 0 through the highest
currently-registered core id (not a hardcoded `BLOCK_COUNT`, since B1 established that
constant is the item ceiling, not the block-kind count; walking past it is exactly
correct here, because the whole point of this screen is to show blocks the player *can't*
carry too, like water and snow). **[NO SOURCE / not found in this pass]** for whether the
registry already exposes an iteration API over registered ids, as opposed to only
point-lookup by id (`registryGet`, `registry.h:122`) — if it does not, the block-list
screen needs one, which is a small, mechanical addition (walk `REG_ID_CORE_LO..HI`,
skip unregistered slots) rather than a design question.

## Part F — What is left genuinely open

1. **Whether apples (ROADMAP.md:257) need `BLOCK_COUNT` to move at all**, and if so, what
   the new ceiling should be. Not in the owner's stated requirements for this brief, so
   not analysed in depth here — flagged because B1's finding (BLOCK_COUNT is the item
   ceiling, not the block-kind ceiling) means this is the *only* piece of the whole
   version that plausibly needs it, and it is worth the owner confirming that before any
   lockstep server change is scoped.
2. **Whether cactus's break-refusal (B2) is a bug to fix or working-as-designed scenery**,
   given `block.h`'s own comment calls the identical behaviour on water and snow a
   deliberate choice. The roadmap text calls it "Fixed," which this brief cannot itself
   resolve without knowing which fix is intended — widen `BLOCK_COUNT`, or widen the
   `blockDropsNothing()`-style predicate the way `block.h:81-85` already prescribes for
   water and tall grass.
3. **The exact PICA200 vertex-shader instruction-slot ceiling** (as opposed to the
   uniform-register ceiling, which is well sourced at 96 and independently corroborated
   inside this project's own comments) — [NO SOURCE] found for a citable number in this
   research pass. C1's Design 1 needs only a handful of extra instructions (one mask, one
   `mova`, one `mul`), the same order of magnitude as the "three vertex-shader
   instructions" the sky-and-weather brief already priced for its own brightness curve,
   so this is very unlikely to be the constraint that bites — but it was not measured
   against a real assembled shader for this brief, and should be before the change ships.
4. **Whether `MeshOut`/registry expose an id-enumeration API** for the block-list screen

   exists.
5. **Real remesh-time and vertex-count cost of adding a second grass height and
   biome-specific flowers** (D4) — reasoned from the existing single-height density

6. **Whether Blocksmith's own `worldgenBiome` field being the inverted terrain field**

   `docs/research/sky-and-weather.md` D5b) changes anything about how the tint LUT's grid
   should be laid out — e.g. whether "cold" tint entries should be biased toward the
   grid's high-terrain end rather than assumed independent of it. Not analysed here;
   flagged because C2's grid-quantisation step reads the same two fields that open
   question is about.
